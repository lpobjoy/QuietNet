# Testing

## Running the tests

From the repository folder:

```bash
python3 -m unittest discover tests
```

Nothing needs installing. The run takes about 85 seconds and ends with a line such as:

```
Ran 1660 tests in 85.0s

OK (skipped=2)
```

About ten of those seconds are one test in `test_devices.py` that moves a two-million-row history, the most QuietNet keeps, in a throwaway folder that needs about 1 GB free for a moment (the test is skipped where there is not that much). For a quicker run while working on something else, give it fewer rows:

```bash
QUIETNET_BIG_ROWS=20000 python3 -m unittest discover tests
```

To run one file, or one test:

```bash
python3 -m unittest tests/test_relay.py
python3 -m unittest tests.test_relay.Relaying.test_another_account_cannot_reach_your_pi
```

`pytest tests` also works if you have it.

## What the tests are safe to do

- They use throwaway data folders. Your real history and rules are never read or changed. The older-household tests in `test_devices.py` build their own database in a second throwaway folder and put the usual one back afterwards.
- No test reads the real neighbour table: every look at "which device has which address" is handed a stand-in table.
- They contact nothing outside the computer. Where the code would reach the internet, a stand-in on the same computer answers. `test_shutdown.py` starts the real program for a moment with `--no-device-names`, so it sends no name questions. `test_names.py` replaces every network socket with a stand-in that records what would have been sent; its only real connections are to a stand-in web server on `127.0.0.1`. No test opens a multicast or broadcast socket.
- With Python 3.9 (Apple's), two checks in `test_packaging.py` that need Python 3.10's list of standard modules are skipped, and the run reports `skipped=2`.
- `test_shutdown.py` is skipped (three more skips) on a Linux machine with admin rights and a firewall tool, because there the real enforcer could start. Run the tests as an ordinary user to include it.
- They need no admin rights. The enforcer's raw socket, firewall command and kernel settings are replaced with stand-ins that record what they were asked to do.
- Web servers are started on spare ports chosen by the operating system, so they do not clash with a running QuietNet.

## Expected failures

There are none at present. When a fault is found that cannot be fixed straight away, write the test for the correct behaviour, mark it `@unittest.expectedFailure`, and point it at an entry in [Known issues](KNOWN_ISSUES.md). The run stays green, and reports "unexpected success" once the fault is fixed, which is the cue to remove the mark.

## Automatic runs

`.github/workflows/tests.yml` runs the suite on every push to `main` and every pull request, on Linux with Python 3.13 (what the containers use) and on macOS with the Python that Apple supplies (what the Mac launcher prefers).

## Writing more

The existing files share a few helpers, all in `test_quietnet.py`:

- `Base`: a test class whose `setUp` empties the rule tables and reloads the rules, so each test starts clean.
- `query(name, qtype)`: builds a DNS question packet.
- `fake_answer(data)`: the reply a real upstream would give, with a one-day lifetime.
- `is_blocked(name, client)`: asks the filter and reports whether the answer was the block address.
- `at(day, "HH:MM")`: a moment on a given weekday, for schedule tests.

Conventions: one behaviour per test; the test name states the behaviour in plain words; a comment explains any check whose reason is not obvious from the name.

## Not covered

These need a real network or a real host, and are not tested automatically:

- The enforcer on a real Pi with real devices. On 22 November it was tested between two containers on one Docker network, standing in for the Pi and a device: steering; non-blocked traffic still flowing; the kill switch cutting the device and lifting cleanly (up to about three seconds could still get through just after it was turned on, issue 45); nothing getting through over 60 to 146 seconds once cut off; hand-back when switched off; refusing to steer while forwarding was off, and while a Docker-style "drop" rule was loaded (then steering once the advised accept was added); recovery after `docker kill`; and a clean `docker stop`. What remains is a real Pi, real devices and Docker's real rules (issues 4 and 15).

  To repeat that test: build the image, create a Docker network, start a plain `python:3.13-slim` container on it as the "device", and start QuietNet on the same network with `--cap-add NET_ADMIN --cap-add NET_RAW --sysctl net.ipv4.ip_forward=1`. Have QuietNet send the device any packet so it learns the device's hardware address, enforce the device through the API (inside the QuietNet container, POST JSON to `http://127.0.0.1:8377/api/enforce` with `Host: localhost`), and watch the device's `/proc/net/arp` entry for the router change to QuietNet's hardware address. Test cutting with a UDP DNS question from the device to `1.1.1.1`.
- The network scan (`scan_network`) and finding device names (`names.py`) on a real network, which depend on the devices present. To check names on a Pi: start QuietNet, wait two minutes, and open the Devices page. Devices that were "Unnamed device" should now show a suggested name with where it came from (Bonjour, Windows network, UPnP, DHCP or the router). Press **Use this name** on one and confirm it becomes its name. Check `docker logs quietnet` for any "Device names: not listening" line, and that `avahi-browse -a` on the Pi still works. Join a phone to Wi-Fi again and confirm a DHCP name appears within two minutes (a device that just stays connected is not heard: its lease renewals go straight to the router). Then start a DHCP server on the Pi after QuietNet (for example `sudo dnsmasq --port=0 --dhcp-range=192.0.2.10,192.0.2.20 --no-daemon` for a moment, on a Pi that is not the network's DHCP server) and confirm it starts without "Address already in use". Known issue 89 has the full list.
- The dashboard page in a browser. Its API calls are checked against the server, and its text is checked for what older Safari can't read, but its behaviour is not. It has not been tried on Safari 12 to 14.0 since the fourth review's fixes, nor the margin spacing added on 23 November for browsers without flex `gap`.
- How the three looks (Calm, Household, Control room) are drawn, on the dashboard and the relay. The tests check the page text only; see "Checking the looks" below and known issue 90.
- Building and starting the containers.
- The installer against a real system: real Docker, Docker's own install script, `sudo`, systemd-resolved and `ss` on real Raspberry Pi OS, Debian and Ubuntu (known issue 85). The automated tests use stand-ins for all of these.
- The relay under load, or with many Pis, and behind Railway's real proxy (the per-address limits depend on it: known issue 79).
- Everything about a real BT Smart Hub's IPv6: whether it offers Allocation Mode "Off" and "ULA Enabled" under the names "Set up a device" uses, the "IPv6 is off on your hub" confirmation after really switching it off, a real phone's new IPv6 address appearing in `ip -6 neigh` in time for the quick look, the hub's link-local and hardware addresses in its announcements, and how devices behave with no IPv6 answers (known issue 95; manual steps 16 to 24 below).
- The router's real IPv6 announcements reaching the listener in the container, the redirect of other DNS servers through real `nft` and conntrack on `wlan0`, rules following real phones that change their private Wi-Fi address, and how apps behave when given no IPv6 addresses (known issues 5, 79 and 93). The redirect's `nft` text was loaded once into a real `nft` (1.1.3) in a container with no network: it loaded, loading it again replaced it, and deleting the table removed it.
- The device tables on a real Pi: how long the one-off move of a real household's database takes on an SD card and what waits meanwhile, a power cut part-way, a full disk, the neighbour table's freshness for real phones (which the record of who has which address rests on), and the cost of reading it every 5 seconds (known issue 96; manual steps 27 to 33).
- Home-network names (single-word names included) through a real router, DNS over IPv6 on a real home network, the relay giving up root on Railway's volume, the Pi's time zone inside the container, and the other points listed in known issues 78 and 79.

A short manual check after changing the enforcer or the containers:

1. `docker compose up -d` on the Pi; confirm `docker logs quietnet` shows "QuietNet is running".
2. Point one device at the Pi for DNS and confirm it appears on the Devices page.
3. Block a service for that device and confirm a new connection fails.
4. Turn on "Cut live connections", start a stream, block its service, and confirm the stream stops within a few seconds while other sites still load. With YouTube blocked, Google search and Classroom should still load, and the card should say some of YouTube's addresses are shared. Unblock it and confirm the service works again without restarting QuietNet.
5. With "Cut live connections" on for a phone or laptop, set its DNS by hand to 8.8.8.8 and look up a blocked name (or run `nslookup disneyplus.com 8.8.8.8` on a laptop): it should get `0.0.0.0` and appear on the device page. Set Android's Private DNS to `dns.google`: the phone should say it can't connect to it, or fall back, and the device page should say it tried to use another DNS service. `sudo nft list table inet quietnet` should show the `dns_redirect` chain naming only steered devices.
6. With the router's IPv6 on, from the steered device run `dig AAAA www.youtube.com @<the Pi>` (or watch its behaviour): it should get no addresses, while another device gets them. Start a new stream and confirm bedtime or the kill switch stops it within seconds (`sudo conntrack -L -f ipv6` on the Pi should show nothing new from the device). Note how long a stream started over IPv6 *before* switching it on carries on. The device's card should show the IPv6 note.
7. On the home page, with the router's IPv6 on: within about ten minutes `/api/status` should show `ipv6.listening: true` and the router's IPv6 DNS server under `router_dns`, and the warning should appear. "Set up a device" should show a lasting IPv6 address for the Pi (not a temporary one). Give it to a Windows laptop as its preferred IPv6 DNS server and check `ipconfig /all` lists only the Pi's addresses as DNS servers.
8. Remove the Docker accept rule (`sudo iptables -D DOCKER-USER -i wlan0 -o wlan0 -j ACCEPT`, or restart the Pi without `quietnet-forward`): the home page should say "Cut live connections" is not working for any device, with the command and the re-run-the-installer line. Run the command and check the notice clears within about 30 seconds.
9. Give a phone a name and a blocked service, then switch its private Wi-Fi address off and on (or forget and rejoin the network). Within about a minute the name and rules should be at its new address, with a note on the home page; a device with "Cut live connections" on should be steered at its new address. Choose "New devices go into group" on the Groups page and join a new device: it should go into that group.
10. `docker stop quietnet`, then confirm the device still has internet and `nft list tables` on the Pi shows no `quietnet` table.
11. After a device with rules changes address (restart the router, or rejoin with a new private address), run `ip neigh` on the Pi: its old address may still be listed as `STALE`. Within a minute the rules should be at the address listed `REACHABLE`. If the phone gets its old number back with a new private address, the home page should ask "Is it the same device?" and the rules should still apply.
12. If the house has a Wi-Fi range extender, run `ip neigh` on the Pi while two devices are behind it: if both show the extender's hardware address, the device pages should say within a few minutes that their rules stay with their addresses, and no rules should move or pause when one of them leaves.
13. With YouTube blocked and "Cut live connections" on, compare `dig r1---sn-<cache>.googlevideo.com` with the `gvt1.com` name from the same cache (from the device's history) against `sudo nft list table inet quietnet`: the video address should be listed even when the download name shares it, and a video already playing should stop.
14. With the router's IPv6 switched off and an Apple TV or HomePod mini on the network, the device page's live-cut card should not say it covers IPv4 only, no device should be marked "Can bypass over IPv6", and "Set up a device" should offer no IPv6 address.
15. On a phone with no rules of its own, set Android's Private DNS to `dns.adguard.com`: it should keep working at home. Turn on "Stop every device using another DNS service" and it should say the Private DNS server can't be reached.
16. **Switching IPv6 off on the hub, and the confirmation.** Leave QuietNet running throughout; do not restart it. In the Hub Manager (192.168.1.254) choose Advanced Settings, IPv6, Configuration and set Allocation Mode to Off (note whether your hub offers it at all, and the exact words on the page, so the steps on "Set up a device" can be corrected). `/api/status` should show `ipv6.listening: true` and `listening_for` counting up. "Set up a device" should go on saying "IPv6 is on in your home" until the hub has been quiet for an hour and the Pi's own public IPv6 address has gone, which can take longer than the hour (known issue 95). It should not say "Still checking" at any point here, since QuietNet has not been restarted. If it says instead that something in your home still names an IPv6 DNS server, see step 25. Once `router_heard` is more than 3,600 seconds old and the Pi's public IPv6 address has gone (`ip -6 addr show dev wlan0` on the Pi shows only `fe80::` addresses, and perhaps one starting `fd`), the page should say **IPv6 is off on your hub**, `ipv6.hub_off` should be `true`, and no device should be marked "Can bypass over IPv6". Write down how long the Pi kept its public address after the switch; if it is many hours, say so in known issue 95. Then `docker restart quietnet`: the confirmation must disappear, the page should say "Still checking" with the minutes left, and the confirmation should come back only after another full hour. Switch IPv6 back on: within about ten minutes the confirmation goes and the devices are marked again.
17. **After switching IPv6 off.** Turn Wi-Fi off and on again on an Android phone and check its network details list only the Pi as DNS server, and that its lookups appear on its card. Check a games console's party chat and a work laptop's VPN still work. If the house has Thread or Matter gear (an Apple TV or HomePod mini acting as its border router), check those devices still answer in the Home app; with one on the network the confirmation in step 16 should still appear, since its announcements carry a router lifetime of 0, but only if it names no IPv6 DNS server of its own (`ipv6.router_dns_not_ours` in `/api/status` must be empty; if it is not, write down which device named the server). Note any device that needed a restart.
18. **The quick look for a new IPv6 address.** With the hub's IPv6 on and any device in a group (so unmatched IPv6 lookups are refused), give a laptop or phone the Pi's IPv6 address as a DNS server, then turn its Wi-Fi off and on so it makes a new temporary address. Run `dig www.bbc.co.uk @<the Pi's IPv6 address>` straight away, and `ip -6 neigh show` on the Pi: the device's new address should be listed within 2 seconds of the lookup. The first lookup should come back `NOERROR`; if it says `REFUSED`, the next one a few seconds later should not. The lookups should be filed on the device's ordinary card, and no new card with only an IPv6 address should appear. Repeat with an Android phone (watch its card, since it has no `dig`).
19. **A stale entry and a fresh one.** For a device that has changed number (the TV at .65 and .67), run `ip -4 neigh` on the Pi: its hardware address may be listed at both, one `STALE` and one `REACHABLE`. Its lookups over IPv6 should be filed on the card of the `REACHABLE` number, however many times you look.
20. **The hub's own addresses.** With the hub's IPv6 on, `ipv6.routers` in `/api/status` should hold one entry within about ten minutes: the hub's link-local address (compare `ip -6 route show default` on the Pi, "via fe80::...") and its hardware address (compare `ip neigh show <the hub's IPv4 address>`). Note whether the two hardware addresses are the same; the later IPv6 steering work relies on that. An Apple TV or HomePod mini must not be listed.
21. **The optional "Give no device IPv6 addresses" switch.** Turn it on, on "Set up a device". From any device, `dig AAAA www.bbc.co.uk @<the Pi>` should give no addresses and `dig A www.bbc.co.uk @<the Pi>` the usual ones; a home name the hub answers (`dig AAAA <a printer>.local @<the Pi>`, or the hub's own name) should be answered as before. Use a phone, a TV and a console for a few minutes and note anything that stops working. Turn it off: the next `dig AAAA` should give addresses again.
22. **Honest labels.** With the hub's IPv6 on, every device that uses QuietNet should carry "Can bypass over IPv6" on the Devices page and the notice on its own page, and a device with "Cut live connections" on should say that it covers IPv4 only. To see that the label is true, block a site for an Android phone that is pointed at the Pi by IPv4 DNS only, and open it: it will probably still load, through the hub's IPv6 DNS server.
23. **When the list of IPv6 neighbours can't be read.** `docker exec quietnet sh -c 'mv "$(command -v ip)" /tmp/ip.off'`, wait two minutes: the home page should say QuietNet can't tell which device a lookup over IPv6 came from, and `ipv6.neighbours_ok` should be `false`. Put it back by making the container afresh (`docker compose up -d --force-recreate`) and check the notice goes.
24. **IPv6 still tried when the IPv4 port is taken.** Stop QuietNet, start another program on the Pi's IPv4 port 53 only (for example `sudo dnsmasq --no-daemon --listen-address=<the Pi's IPv4 address> --bind-interfaces`), and start QuietNet: the dashboard should say the filter couldn't start, and `docker logs quietnet` should not say IPv6 listening failed. Stop the other program and restart QuietNet.
25. **Allocation Mode off with ULA left on.** On the hub, set Allocation Mode to Off and leave (or turn) **ULA Enabled** on. Do not restart QuietNet. After the hub has been quiet for an hour (as in step 16), look at `ipv6.router_dns_not_ours` and `ipv6.router_dns` in `/api/status`, and at `ip -6 addr show dev wlan0` on the Pi (an address starting `fd` means the hub is still announcing its private range). If the hub still names an IPv6 DNS server, "Set up a device" must say **Something in your home still names an IPv6 DNS server that is not QuietNet**, never "IPv6 is off on your hub"; `ipv6.hub_off` must be `false`; and devices must still be marked "Can bypass over IPv6". Then turn ULA Enabled off: within about an hour the notice should go and the confirmation appear. Write down what the hub actually announces in this state (`sudo tcpdump -vv -i wlan0 icmp6 and 'ip6[40] == 134'` on the Pi shows the router lifetime and any DNS server), and correct the wording of the notice and of known issue 95 if the hub behaves differently.
26. **IPv6 switched off on the Pi itself.** With the hub's IPv6 **on**, run `sudo sysctl -w net.ipv6.conf.wlan0.disable_ipv6=1` on the Pi (use the Pi's own network card name; `nmcli` with `ipv6.method disabled` does the same) and do not restart QuietNet. Within about two minutes `/api/status` should show `ipv6.can_hear: false` and `listening_for: 0`. Wait over an hour: "Set up a device" must say **QuietNet can't tell whether IPv6 is on in your home**, with the reason, and never "IPv6 is off on your hub"; `ipv6.hub_off` must stay `false`. Then `sudo sysctl -w net.ipv6.conf.wlan0.disable_ipv6=0`: within about ten minutes `can_hear` should be `true` and the page should say "IPv6 is on in your home" again. Repeat once with `net.ipv6.conf.all.disable_ipv6=1` to confirm the Pi's card loses its `fe80::` address that way too.
27. **Moving a real household's data, on a copy first.** Before upgrading the Pi to a version with the device tables, copy its data folder to another machine or folder (`docker stop quietnet`, copy `data/`, `docker start quietnet`). Start the new version on the **copy** (`QUIETNET_DATA=<the copy> python3 server.py --no-browser --dns-port 5353 --web-port 8378`, on the Pi itself so the SD card's speed is the real one). The log should say "Moved the household's data to the device tables in N seconds: ..." and, later, "Every older history row now has its device." Note both times and the size of `quietnet.db`. `quietnet.db.before-devices` should be in the copy's folder, the same size as the database was. `/api/status` should show `devices.state: "ready"`, and `devices.filling` going from `true` to `false`.
28. **Start-up time and what waits during the move.** On the real upgrade (`docker compose up -d --build`), time from the container starting to the first answered lookup (`dig www.bbc.co.uk @<the Pi>` in a loop from a laptop): it should be no longer than before the upgrade, because the move starts only after the filter is answering. While the log has not yet printed "Moved the household's data", keep the loop running and reload the dashboard: lookups should be answered throughout and a blocked name should stay blocked; the dashboard may hang for the seconds the index takes to build. Note how long. If a device has "Cut live connections" on, check it is still steered afterwards (`ip neigh` on the device shows the Pi's hardware address for the router).
29. **Lookup speed during the fill.** While `devices.filling` is `true`, run `for i in $(seq 50); do dig +stats www.bbc.co.uk @<the Pi> | grep "Query time"; done` and compare with the same after it finishes. The dashboard's Devices page should load in its usual time throughout, with today's counts right from the first minute.
30. **A power cut half-way.** On a copy (step 27), start the new version and pull the power (or `kill -9` the program) while the log has not yet printed "Moved the household's data". Start it again: the database must open, the move must run again from the beginning and finish, and no rules, names or history may be missing (compare `sqlite3 quietnet.db "select count(*) from queries"` and the Rules page with before). Do the same during the fill: after the restart `devices.filling` should be `true` again and then finish.
31. **A full disk.** On a copy, fill the disk until less than twice the database's size is free (`fallocate -l <size> filler` beside it) and start the new version. The home page should say QuietNet needs free space, that nothing has been changed and that it will try again within the hour; `devices.state` should be `"waiting"`; there should be no `quietnet.db.before-devices`; and devices, rules and history should all work as before. Delete the filler: within an hour (or after a restart) the move should run.
32. **One card per device, and a reused address.** After the move, a device that had two cards because it changed number (the TV at .65 and .67) should be one card at its present number, with the lookups of both in its history. Then make an address change hands: note a phone's number, switch the phone off, and reserve that number for a laptop in the Hub Manager (or wait for the hub to hand it on). The laptop's card should show only the laptop's lookups, from its first one; the phone's earlier lookups must not appear on it. `/api/devices` should list the phone with `"ip": ""` and its own `n`.
33. **Freshness on a real network, and the cost of looking.** Leave a phone idle for ten minutes, then open one web page on it. Within about a minute `sqlite3 quietnet.db "select count(*) from queries where device is null and ts < strftime('%s','now') - 300"` should be 0 (waiting lookups are filed within a few minutes). Run `ip -4 neigh` a few times while doing it and note the states the phone goes through (`STALE`, `DELAY`, `REACHABLE`); if lookups stay unfiled, that is where to look. With two devices behind a Wi-Fi range extender (step 12), their lookups should be filed under their own numbers (`kind` `"addr"` in `/api/devices`), never joined. Check `top` on the Pi: the look every 5 seconds should not show as load.

### Checking the looks (themes)

After changing the dashboard's or the relay's style sheet, open the dashboard (on a Mac, **Start QuietNet.command**, or `python3 server.py --dns-port 5353`; then <http://localhost:8377>) and, if you can, a test relay with a paired Pi. Use a desktop browser and a phone, or a browser window about 375 pixels wide. For **each** of Calm, Household and Control room:

1. **Choosing it.** Pick it under **Set up a device → Appearance** (also reached from the Appearance button at the top). The page changes at once, with no reload, and the radio button stays ticked. Reload: the same look comes back, with no flash of another look's colours first. On the relay's home page, pick it under Appearance and press **Use this look**: you are taken back to the home page in that look, and the dashboard opened from there (`/pi/<id>/`) is in it too.
2. **Light and dark.** Switch the device between light and dark (on a Mac, System Settings → Appearance). Calm and Household follow it on every page; Control room stays dark. Text, buttons, tags, the kill switch's warning colours and the relay's bar across the top of a relayed dashboard should all stay easy to read in both.
3. **Every page.** Devices, a device's page, Groups, a group's page, Schedules, Blocked, Set up a device, the kill-switch confirmation; on the relay, sign in, create account, home (with a paired Pi and a waiting one), and an error page (any unknown address, such as `/nothing-here`). Nothing overlaps or is cut off.

### Checking licences after deploying the relay

The licence gate can't be tried on Railway by the automated tests. After deploying a relay with licences:

1. **Gate off.** Leave `QUIETNET_LICENCE_GATE` unset. The start-up log should say "Licence gate: off". Open the relay, sign in, and confirm your Pis still open and the Licence card shows a sentence and "Pis: N of M".
2. **Legacy licences.** In the Railway container (`railway ssh`), run `python relay.py licence show <your email>`. It should say "Plan: legacy", active, ending about 90 days after the first start, with a log line "Legacy licence given ...". Restart the relay and run it again: the end date must not have moved.
3. **Grant the owner.** Run `python relay.py licence grant <your email> --plan owner --seats N` (N more than your number of Pis, so there is a free seat for the test Pi in step 4), then `show` again: "Plan: owner", "Ends: no end date". Then `ls -l /data` and check `relay.db` and its `-wal` and `-shm` files are still owned by the relay's user (65534 unless `QUIETNET_RUN_AS` says otherwise), not root.
4. **Read the log.** Use the relay normally for a few days: open a Pi, add and remove a test Pi. Then run `licence list`, then `show` for any account you don't recognise, and read the Railway log for lines starting "Licence gate:". With the owner granted there should be none for your account; any that appear say what would have been refused.
5. **Gate on.** Set `QUIETNET_LICENCE_GATE=on` and redeploy. The log should say "Licence gate: on". Your Pis should still open. You need a test account with no licence and a paired test Pi, set up **before** turning the gate on (with the gate on, an account with no licence can't add or pair a Pi). Either set `QUIETNET_SIGNUP=open` briefly, create the test account (accounts made after the first start get no licence), add and pair a test Pi to it, then set sign-up back; or use a test account that existed at the first start and already has a paired Pi, and take its legacy licence away with `python relay.py licence revoke <test email> --reason "gate test"` (and `licence restore <test email>` afterwards). With the gate on, that account's paired test Pi should show "Remote access paused" on the home page and the paused page when opened; both rescue buttons should work (the Pi's dashboard at home should show the kill switch off, or blocking paused). The test Pi must stay paired and keep filtering.
6. **Quick way back.** If anything pauses a paying account by mistake, remove `QUIETNET_LICENCE_GATE` (or set it to `off`) and redeploy; nothing else needs undoing.

### Checking the installer on a real Pi

`install.sh` changes a real system, so after changing it, try it on a freshly flashed Raspberry Pi OS (64-bit, and 32-bit if you can), and ideally on Debian and Ubuntu too (Ubuntu runs systemd-resolved on port 53). To try a branch before it reaches `main`, fetch that branch's copy and pass `--ref`:

```bash
curl -fsSL https://raw.githubusercontent.com/lpobjoy/QuietNet/BRANCH/install.sh | sh -s -- --ref BRANCH
```

1. **Fresh install, with pairing.** On the relay, choose **Add a QuietNet** and copy the line the card shows (when testing a branch, change `main` in its address to `BRANCH` and add `--ref BRANCH` at the end, or set `QUIETNET_INSTALL_URL` on a test relay). Check that the line shows the relay's real address, not `https://your-relay-address`. Run it on the Pi as an ordinary user with `sudo`, on a Pi without Docker. Confirm it asks before installing Docker, that Docker installs, that the container is running (`sudo docker ps`), that the closing message gives the Pi's right home-network address, and that the Pi appears as online on the relay's page within a minute.
2. **What it changed.** `/opt/quietnet` holds the program; `cat /etc/sysctl.d/90-quietnet.conf` shows `net.ipv4.ip_forward=1`; `sysctl net.ipv4.ip_forward` says 1; `sudo docker volume ls` shows `quietnet_quietnet-data`; `sudo docker inspect quietnet` shows the project label `quietnet`. It asked about Docker's firewall naming the Pi's connection (`wlan0` on Wi-Fi, `eth0` or `end0` on a cable); `systemctl status quietnet-forward` shows it active (exited), and `sudo iptables -S DOCKER-USER` shows `-A DOCKER-USER -i wlan0 -o wlan0 -j ACCEPT` once. Restart the Pi and check that rule again, still once; turn on **Cut live connections** for a device and confirm the device page shows no firewall warning. On Ubuntu, confirm it asked about systemd-resolved, that `/etc/systemd/resolved.conf.d/quietnet.conf` exists, and that the Pi can still look up names itself (`getent hosts github.com`).
3. **DNS works.** Point a device at the Pi and confirm its lookups appear on the dashboard, through the relay.
4. **Re-run to update.** Make a rule on the dashboard, then run the same line again (a fresh code, or none). Confirm it finishes, that the rule is still there, that the Pi is still paired, and that no `/opt/quietnet.new.*` folder is left behind.
5. **No terminal.** Run `curl -fsSL …/install.sh | sh` from a script with no terminal (for example through `ssh pi@host 'curl … | sh'` without `-t`) on a Pi without Docker, and confirm it stops and says to add `--yes`, having changed nothing.
6. **Uninstall.** Run it with `--uninstall`. Confirm the container and `/opt/quietnet` are gone, the volume is still listed, and the message says how to delete the volume and undo the forwarding, `quietnet-forward` and systemd-resolved files. Run the install again and confirm the rule from step 4 is back.
7. **Next to a hand-started copy.** Start QuietNet by hand with `docker compose up -d` from a folder not called `QuietNet`, then run the installer: it should stop, naming that folder, and change nothing. Then remove it and start a container called `quietnet` with plain `docker run --name quietnet ...` (no Compose): the installer should stop and suggest `sudo docker rm -f quietnet`, and `--uninstall` should leave it alone with a warning.
8. **sudo.** As a user who is not allowed to use sudo, run the line: it should stop at once, after sudo's own refusal, saying administrator rights could not be obtained. As a user whose sudo needs a password, run it over `ssh pi@host 'curl … | sh'` without `-t`: it should stop the same way and suggest `ssh -t`; with `-t` it should ask for the password and carry on.
