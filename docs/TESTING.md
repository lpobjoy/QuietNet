# Testing

## Running the tests

From the repository folder:

```bash
python3 -m unittest discover tests
```

Nothing needs installing. The run takes about two minutes (as measured on 25 November: about 100 seconds on Linux with Python 3.13, 110 on a Mac with a current Python, 125 with the Python that Apple supplies) and ends with a line such as:

```
Ran 2482 tests in 123.9s

OK (skipped=2)
```

About ten of those seconds are one test in `test_devices.py` that moves a two-million-row history, the most QuietNet keeps, in a throwaway folder that needs about 1 GB free for a moment (the test is skipped where there is not that much). For a quicker run while working on something else, give it fewer rows:

```bash
QUIETNET_BIG_ROWS=20000 python3 -m unittest discover tests
```

To run one file, or one test:

```bash
python3 -m unittest tests/test_relay.py
python3 -m unittest tests.test_relay.Relaying.test_another_account_cannot_reach_your_pi
```

`pytest tests` also works if you have it.

## What the tests are safe to do

- They use throwaway data folders. Your real history and rules are never read or changed. The older-household tests in `test_devices.py` build their own database in a second throwaway folder and put the usual one back afterwards. `test_shutdown.py` removes the folder of every program it starts (until 25 November it left them behind in the computer's temporary folder, a quarter of a megabyte each; any still there, named `quietnet-shutdown-test-...`, can be deleted). Every other test removes what it makes as well, and the two data folders made as the test files are first read are removed as the run ends. (Until 25 November a whole run left 96 small folders behind, named `quietnet-agent-test-...`, `quietnet-relay-cli-...`, `quietnet-relay-licence-...`, `quietnet-relay-old-...`, `quietnet-relay-test-...` and `quietnet-test-...`; any still there can be deleted.) A run that is killed part-way cannot tidy up after itself and still leaves its folders.
- The tests themselves never read this computer's real neighbour table: every look at "which device has which address" is handed a stand-in table, the enforcer's plan is given a stand-in for the live table, and `Base.setUp` puts an empty stand-in in place of `server.neighbours` (which giving a rule to an address no device is known for would otherwise read). The one exception is `test_shutdown.py`, which starts the real program for a moment. As it starts, that program reads this computer's own list of neighbours and its own addresses once (with `arp`, `ndp` and `ifconfig` on a Mac, `ip` on Linux). That sends nothing onto the network, and anything it keeps goes only into its throwaway data folder.
- They contact nothing outside the computer. Where the code would reach the internet, a stand-in on the same computer answers. `test_shutdown.py` starts the real program for a moment with `--no-device-names`, so it sends no name questions; the one test there that sends it lookups first puts a stand-in on this computer in place of the internet's DNS servers. `test_names.py` replaces every network socket with a stand-in that records what would have been sent; its only real connections are to a stand-in web server on `127.0.0.1`. No test opens a multicast or broadcast socket.
- With Python 3.9 (Apple's), two checks in `test_packaging.py` that need Python 3.10's list of standard modules are skipped, and the run reports `skipped=2`.
- `test_shutdown.py` is skipped (fourteen more skips) on a Linux machine with admin rights and a firewall tool, because there the real enforcer could start. Run the tests as an ordinary user to include it. `test_start_stop.py` runs everywhere: it starts stand-ins for the enforcer, and in the one test that starts the real one (to see the clean-up wait while a steered device's IPv6 and IPv4 are handed back) everything the enforcer would touch has a stand-in, so no command is run, no setting is changed and no frame is sent.
- `test_start_stop.py` sends the test program itself the two signals that ask QuietNet to stop, but only while QuietNet's own handling of them is in place, and puts back the handling that was there before after every test.
- They need no admin rights. The enforcer's raw socket, firewall command and kernel settings are replaced with stand-ins that record what they were asked to do.
- Web servers are started on spare ports chosen by the operating system, so they do not clash with a running QuietNet.

## Expected failures

There are none at present. When a fault is found that cannot be fixed straight away, write the test for the correct behaviour, mark it `@unittest.expectedFailure`, and point it at an entry in [Known issues](KNOWN_ISSUES.md). The run stays green, and reports "unexpected success" once the fault is fixed, which is the cue to remove the mark.

`.github/workflows/tests.yml` runs the suite on every push to `main` and every pull request, on Linux with Python 3.13 (what the containers use) and on macOS with the Python that Apple supplies (what the Mac launcher prefers).

## Writing more

The existing files share a few helpers, all in `test_quietnet.py`:

- `Base`: a test class whose `setUp` empties the rule tables and reloads the rules, so each test starts clean. Rules are held against devices, so it also has `device(ip)` (the number of the device listed under an address, made if none is known), `match_ipv6(v6, ip)` (have an IPv6 address matched to that device, as a look at the IPv6 neighbours would) and `live_cut(ip, mac)` (switch "cut live connections" on for the device a stand-in neighbour table shows there). A rule given as `device:<ip>` in a test is kept against the device listed there, as it is for an older dashboard page.
- `query(name, qtype)`: builds a DNS question packet.
- `fake_answer(data)`: the reply a real upstream would give, with a one-day lifetime.
- `is_blocked(name, client)`: asks the filter and reports whether the answer was the block address.
- `at(day, "HH:MM")`: a moment on a given weekday, for schedule tests.
- `in_force_now()`: the days and times to give a schedule so that it is in force at this moment, whatever the time of day: `self.schedule(**in_force_now(scope="all"))`. `not_in_force_now()` is its opposite.
- `server.init_db()`: call it to mimic a restart, as the program's own start-up does. In the tests it also closes the database connection it replaces (`test_quietnet.py` wraps it), so that a run is not filled with "unclosed database" warnings.

Conventions: one behaviour per test; the test name states the behaviour in plain words; a comment explains any check whose reason is not obvious from the name.

A test must pass at any time of day, on any day of the week, and on a slow machine:

- **Never write a fixed window to mean "now".** A schedule from 00:00 to 23:59 is off for the last minute of every day (its end is not inside it), and six tests built on one failed when GitHub's machines ran them at 23:59. Use `in_force_now()`. A test about a particular window should pass the moment itself, with `at(day, "HH:MM")`, and not read the clock at all.
- **Wait for the thing itself, not for a length of time.** The relay finishes some of its work just after an answer has been sent: it gives back the room held for a large answer, and frees the connection's place. And the dashboard's port takes connections a moment before the program is serving. A test that checks such a thing straight after the answer arrives, or after a fixed `sleep`, fails now and then on a busy machine. Check again for a few seconds until it is so, then assert (see `answer_once_a_place_is_free` in `test_relay.py` and `wait_until_the_dashboard_answers` in `test_shutdown.py`). (`test_shutdown.py` once needed a fixed pause between the dashboard's first answer and the request to stop, because the program could lose a request that arrived while it was still taking that connection. That fault is fixed and the pause has gone: the request is now sent the moment the answer arrives.) To hold the program at a moment inside its start-up, `test_shutdown.py` waits for its first printed line, and `test_start_stop.py` has a stand-in send the request while it is being started; neither sleeps.
- **Remove every temporary file or folder you make, and say so on the next line.** `self.addCleanup(shutil.rmtree, folder, True)` straight after `tempfile.mkdtemp(...)`; for a folder made as a test file is first read, `atexit.register(shutil.rmtree, folder, True)`. A run left 96 folders behind until this was done, and runs in a loop filled a Mac's temporary folder with a hundred thousand. A test in `test_packaging.py` fails for any `tempfile` call with no removal named within four lines.
- **A stand-in thread must not die of an error the test expects.** Python prints a traceback for any error that ends a thread, and a traceback in the log of a run that passed sends people looking for a fault that is not there. The relay closes the connection on an answer it refuses, so `pretend_pi` in `test_relay.py` takes that as nothing wrong.
- **Hold the clock still when the behaviour is "within a second".** Where QuietNet counts things per second, or keeps something for a second or two, a test that makes several calls and lets the clock run fails if the machine stalls between them. Hold the steady clock at one reading for the length of the check: `now = time.monotonic()`, then `mock.patch.object(server.time, "monotonic", lambda: now)` (see `test_only_so_many_words_are_taken_in_each_second` in `test_device_moves.py`). The same goes for a longer wait that a test ends by itself (`steady_clock_held_at_the_move()` in `test_devices.py`). And a test that times its looks from one reading of the clock (`self.now`) should time everything else from that reading too, not from a fresh `time.time()`.
- **A test that starts the real program shows what it printed when it fails.** See `give_up` and `ended` in `test_shutdown.py`.
- **A test that floods the dashboard with connections must keep to fewer than five at once.** Python's web server lets five connections wait their turn; beyond that a Mac resets some, and the dashboard prints a traceback for each, which a test that asks for an output free of tracebacks would then fail on. See `BUSY_CLIENTS` in `test_shutdown.py`.
- **A test that sends its own program a signal must check first what will handle it.** Left to Python, SIGTERM ends the whole test run and Ctrl-C's signal raises `KeyboardInterrupt` in it. See `ask_to_stop` in `test_start_stop.py`, and the helper thread in `WholeLife.run_it`, which sends nothing unless QuietNet is listening.
- **Anything new that `start_up()` starts needs a stand-in in `WholeLife.setUp`** (`test_start_stop.py`), and anything it keeps for `clean_up()` (a global such as `ENF`) needs to be put back to `None` there. Those tests run the real `start_up()` and `clean_up()` inside the test program, so without a stand-in the new thing would be started for real, on the real network if that is what it uses, by a dozen tests that would all still pass. One test there fails until every name the two functions use either has a stand-in or is listed in `STARTS_NOTHING`; add a name to that list only if it truly starts nothing. Something started with nothing but a thread, as the device keeper is, runs its stand-in a moment after `start_up()` has moved on, so the stand-in cannot write its own line in the tests' diary at the right place: `noting_thread()` there writes the line as the thread is started, and can do the same for another thread.
- **A helper thread in a test waits with a limit too.** A wait such as "until the dashboard exists" must give up after a generous time and do nothing more, or a broken start-up costs the full time limit of every test that uses it and leaves the thread spinning.
- **A test that starts the real program and sends it Ctrl-C must start it able to hear Ctrl-C.** A program inherits "ignore Ctrl-C" from whatever started it, and a test run has it ignored when a script or a shell without a terminal starts it in the background (with `&`). QuietNet then rightly leaves it ignored, and the test fails with "QuietNet ignored the request to stop". `Shutdown.setUp` in `test_shutdown.py` gives the test program Python's usual Ctrl-C handler for the length of each test, which the program it starts does not inherit as "ignore".
- **"Address already in use" from a program a test has just started is a clash over a spare port, not a fault.** A spare port is found by opening one and closing it, and the program opens it a moment later. `Shutdown.start` tries such a start once more, and looks for a port that is spare for both UDP and TCP for the DNS filter, which opens both (a start that needs the filter, to send it lookups, is also tried again if the program says it could not open the filter's port). `LiveFilter` in `test_dns.py`, which runs the real filter inside the test program, looks for its port in the same way; if the port still cannot be opened its six tests are skipped, and the run says `skipped=1`. If it still fails, or a test fails with "Can't assign requested address" or "dashboard answered 404", the computer is short of spare ports: on a Mac, one run of the shutdown tests uses about a thousand of the 16,384 for half a minute, so more than three or four runs side by side can use them up. Wait half a minute and run again.

The stream and the device's other sites should keep working. `docker logs --tail 5 quietnet` should end with "Enforcer stopped; network restored." and then "QuietNet stopped.", with no "Traceback" above them, and `docker inspect -f '{{.State.ExitCode}}' quietnet` should print `0` (`137` means it was killed). `sudo nft list tables` should show no `quietnet` table. Do it again with the dashboard open in a browser, which keeps asking for fresh figures, and again through the relay. Do it once more with the internet down (pull the router's internet cable, or its broadband lead, for a minute first, with a few devices in use so that their lookups are waiting): `docker stop` should still come back within a few seconds with `0`, and nothing should be printed after "QuietNet stopped." (before 25 November this could take up to 20 seconds, show a traceback naming "cannot schedule new futures", and end with `137`). Then the start-up case: `docker start quietnet`, and as soon as `docker logs quietnet` shows "Enforcer ready", `docker stop quietnet`: the same lines and the same `0`. Last, the one case that may still not work (known issue 12): `docker start quietnet && docker stop quietnet` in one go. If the request arrives while Python itself is still starting, before QuietNet's first line, Linux drops it: `docker stop` then takes the full 20 seconds and the exit code is `137`. If it arrives a moment later, while QuietNet is loading, it should come back within a second or two with `0`, and the log's newest line should be "QuietNet stopped." with no "QuietNet is running." before it. Try it several times and note which happens, and with a short `sleep` between the two commands how long after `docker start` a request has to come to be acted on (in a test container held to half a processor it was about a tenth of a second). Where "Take IPv6 away from steered devices" is on, a stop hands those devices' IPv6 back as well, before their IPv4: step 66 has what to look for, and should be run with this one.

Restart QuietNet (`docker compose restart`) and try again at once: still refused. Switch the tablet on: its bedtime still applies.
60. **A merged laptop with both cards connected.** With step 49's laptop merged, unnamed, and on cable and Wi-Fi at once: open "Separate" and leave the box open for a minute before choosing; it must go through at the first press, without "Something changed since this was shown". Name the laptop and give it a schedule: the Schedules page must show the schedule under the laptop's name, never under a bare number.

### Taking IPv6 away from steered devices (option c2, needs a real Pi, devices and hub)

None of this has run on a real network yet (known issue 101); these steps are how to check it and correct the code. From step 61 to 67, keep the hub's IPv6 **on** (this is the case this feature is for), turn on **Cut live connections** for the test device on its page, and turn on **Take IPv6 away from steered devices** under "Set up a device" (step 68 is run with the setting **off**). Capture on the Pi with `sudo tcpdump -vv -i wlan0 'icmp6 && ip6[40] >= 133 && ip6[40] <= 136'` to watch neighbour discovery.

61. **The hub's address is learned first.** With the setting on but before any device is steered, `ipv6.routers` in `/api/status` must list the hub (step 22) and `enforcer.ipv6_steering.hub_known` must be `true`. Note whether the hardware address listed there is the one `ip -4 neigh` on the Pi shows for the hub's IPv4 address, and write the answer into known issue 101 (it decides whether the two can be matched). While it is `false` (no hub announcement heard yet) nothing should be sent: confirm the capture shows no neighbour advertisement from the Pi.
62. **A steered device is claimed, and only it.** With the test device steered, the capture should show the Pi sending a neighbour advertisement for the hub's link-local address, Ethernet-addressed to the test device and IPv6-addressed to its link-local address, hop limit 255, with the "override" flag set and the Pi's hardware address as the target link-layer option. It must never be sent to `ff02::1`, to the hub, to the Pi itself, or to any other device: check the Ethernet and IPv6 destinations of every advertisement. On the test device, `ip -6 neigh show` (Linux/macOS) should show the hub's link-local address at the **Pi's** hardware address, not the hub's. A second, unsteered device's neighbour table must still show the hub's real hardware address. (On a Mac test device the neighbour table is `ndp -an`, not `ip -6 neigh`.) A device that has never spoken IPv6 to the Pi may take a minute or two to be steered while the Pi learns its link-local address; meanwhile `enforcer.ipv6_steering.problems` names it. Take it off Wi-Fi for ten minutes and back, and confirm it is claimed again without help. Then have the hub give the device a new number (as in step 44): the claim should follow it within a few seconds of IPv4 steering doing so, with no claim sent to whoever has the old number. With the merged laptop of step 50, each of its two hardware addresses should be claimed at its own link-local address.
63. **Reachability checks are answered.** Leave the device idle a few minutes. The capture should show it sending neighbour solicitations for the hub's address (to the solicited-node multicast group), and the Pi answering each with an advertisement within a fraction of a second. Confirm the device does not drift back to the hub (its `ip -6 neigh`, or `ndp -an` on a Mac, keeps the Pi's hardware address). Confirm the Pi joined the group: `ip -6 maddr show dev wlan0` should list `ff02::1:ff..` for the hub's address.
64. **DNS is answered from the right address, and browsing works over IPv4.** On the steered device, `dig AAAA www.bbc.co.uk` sent to the hub's IPv6 DNS address should come back with no addresses (the "Cut live connections" rule), and `dig A ...` the usual ones; `sudo nft list table inet quietnet` on the Pi should show the `dns_redirect6` chain naming the device's hardware address. Browse normally on the device and confirm pages load (over IPv4). Block a site for the device and confirm it is now actually blocked, where before turning this on it could be reached over IPv6 (step 24).
65. **A device behind a range extender is left alone.** With a device behind a Wi-Fi range extender (as in step 12) and "Cut live connections" on for it, its page should say exactly **This device is behind a range extender, so QuietNet leaves its IPv6 alone.**, the capture should show no advertisement sent to it, and `enforcer.ipv6_steering.problems` (keyed by the device's IPv4 address) should name it. Before the extender is recognised (its hardware address seen at two numbers at once on three looks) the page should say instead that more than one device seems to share this device's hardware address; either way no advertisement is sent.
66. **Stop now, and clean stop.** Turn the setting off: the capture should show one correction per steered device (an advertisement giving the hub's **real** hardware address), the devices' `ip -6 neigh` (or `ndp -an` on a Mac) should return to the hub's hardware address within seconds, and IPv6 should work on them again. Turn it back on, then `docker stop quietnet` (with step 17, whose checks all apply here too: back within a few seconds, exit code `0`, "Enforcer stopped; network restored." and then "QuietNet stopped." as the last lines): the same correction should go out within the stop wait, before the device is handed back over IPv4, and the Pi should leave no lasting IPv6 setting (`sysctl net.ipv6.conf.all.forwarding` unchanged; no `quietnet` nft table). Time how long a device takes to recover IPv6 after a clean stop.
67. **Recovery after a crash, and a restart.** With a device steered, `docker kill quietnet` (no clean stop). Time how long the device takes to right itself with no help (it should, within seconds to minutes, once the Pi stops answering its checks); note it in known issue 101. Start QuietNet again: `enforcer_state.json` should have carried the steered device and the hub's addresses (`v6_spoofed` and `v6_hub`), and the first tick should send the saved device a correction within a few seconds of start (check the capture), even before the hub is heard; a fresh claim for a device still chosen comes only after the hub's next announcement. Repeat the recovery timing after a power pull and after an upgrade (`docker compose up -d --build`).
68. **Half an hour steered, how the hub takes it, and ordinary lookups with the setting off.** With the test device steered and at least one other, unsteered device in ordinary use, leave the capture running for 30 minutes (type 134 shows the hub's announcements). Note the time between the hub's router announcements and write it in known issue 101. After each announcement the capture should show the Pi sending the claim to the steered device again within a second or so, and the device's neighbour table (`ip -6 neigh show`, or `ndp -an` on a Mac) should still show the hub's link-local address at the **Pi's** hardware address at the end. Through the whole time, confirm that no device, steered or not, drops off Wi-Fi or loses IPv4 (keep `ping 192.168.1.254` running on both and watch for gaps; check the unsteered device still has working IPv6). Open the hub's event log (Hub Manager, Advanced Settings, Technical Log, Event Log) and read the entries: look for an address conflict, a duplicate address, a security warning or a device disconnected. If the hub logs a conflict or drops anyone, switch the setting off at once and record it in known issue 101; the setting must stay off by default until this passes. Then, with the setting **off**, capture `sudo tcpdump -n -i wlan0 'ip6 and udp port 53'`, and from another device run `dig @<the Pi's lasting fd.. or public address> www.bbc.co.uk` and `dig @<the Pi's fe80:: address>%<that device's card> www.bbc.co.uk` (on the Pi, `ip -6 addr show dev wlan0` lists both): both must be answered promptly, and each answer must leave from exactly the address the question was sent to. If either goes unanswered or leaves from another address, write it in known issue 101 and correct `send_answer()`.

### Checking licences after deploying the relay

The licence gate can't be tried on Railway by the automated tests. After deploying a relay with licences:

1. **Gate off.** Leave `QUIETNET_LICENCE_GATE` unset. The start-up log should say "Licence gate: off". Open the relay, sign in, and confirm your Pis still open and the Licence card shows a sentence and "Pis: N of M".
2. **Legacy licences.** In the Railway container (`railway ssh`), run `python relay.py licence show <your email>`. It should say "Plan: legacy", active, ending about 90 days after the first start, with a log line "Legacy licence given ...". Restart the relay and run it again: the end date must not have moved.
3. **Grant the owner.** Run `python relay.py licence grant <your email> --plan owner --seats N` (N more than your number of Pis, so there is a free seat for the test Pi in step 4), then `show` again: "Plan: owner", "Ends: no end date". Then `ls -l /data` and check `relay.db` and its `-wal` and `-shm` files are still owned by the relay's user (65534 unless `QUIETNET_RUN_AS` says otherwise), not root.
4. **Read the log.** Use the relay normally for a few days: open a Pi, add and remove a test Pi. Then run `licence list`, then `show` for any account you don't recognise, and read the Railway log for lines starting "Licence gate:". With the owner granted there should be none for your account; any that appear say what would have been refused.
5. **Gate on.** Set `QUIETNET_LICENCE_GATE=on` and redeploy. The log should say "Licence gate: on". Your Pis should still open. You need a test account with no licence and a paired test Pi, set up **before** turning the gate on (with the gate on, an account with no licence can't add or pair a Pi). Either set `QUIETNET_SIGNUP=open` briefly, create the test account (accounts made after the first start get no licence), add and pair a test Pi to it, then set sign-up back; or use a test account that existed at the first start and already has a paired Pi, and take its legacy licence away with `python relay.py licence revoke <test email> --reason "gate test"` (and `licence restore <test email>` afterwards). With the gate on, that account's paired test Pi should show "Remote access paused" on the home page and the paused page when opened; both rescue buttons should work (the Pi's dashboard at home should show the kill switch off, or blocking paused). The test Pi must stay paired and keep filtering.
6. **Quick way back.** If anything pauses a paying account by mistake, remove `QUIETNET_LICENCE_GATE` (or set it to `off`) and redeploy; nothing else needs undoing.

### Checking the installer on a real Pi

`install.sh` changes a real system, so after changing it, try it on a freshly flashed Raspberry Pi OS (64-bit, and 32-bit if you can), and ideally on Debian and Ubuntu too (Ubuntu runs systemd-resolved on port 53). To try a branch before it reaches `main`, fetch that branch's copy and pass `--ref`:

```bash
curl -fsSL https://raw.githubusercontent.com/lpobjoy/QuietNet/BRANCH/install.sh | sh -s -- --ref BRANCH
```

1. **Fresh install, with pairing.** On the relay, choose **Add a QuietNet** and copy the line the card shows (when testing a branch, change `main` in its address to `BRANCH` and add `--ref BRANCH` at the end, or set `QUIETNET_INSTALL_URL` on a test relay). Check that the line shows the relay's real address, not `https://your-relay-address`. Run it on the Pi as an ordinary user with `sudo`, on a Pi without Docker. Confirm it asks before installing Docker, that Docker installs, that the container is running (`sudo docker ps`), that the closing message gives the Pi's right home-network address, and that the Pi appears as online on the relay's page within a minute.
2. **What it changed.** `/opt/quietnet` holds the program; `cat /etc/sysctl.d/90-quietnet.conf` shows `net.ipv4.ip_forward=1`; `sysctl net.ipv4.ip_forward` says 1; `sudo docker volume ls` shows `quietnet_quietnet-data`; `sudo docker inspect quietnet` shows the project label `quietnet`. It asked about Docker's firewall naming the Pi's connection (`wlan0` on Wi-Fi, `eth0` or `end0` on a cable); `systemctl status quietnet-forward` shows it active (exited), and `sudo iptables -S DOCKER-USER` shows `-A DOCKER-USER -i wlan0 -o wlan0 -j ACCEPT` once. Restart the Pi and check that rule again, still once; turn on **Cut live connections** for a device and confirm the device page shows no firewall warning. On Ubuntu, confirm it asked about systemd-resolved, that `/etc/systemd/resolved.conf.d/quietnet.conf` exists, and that the Pi can still look up names itself (`getent hosts github.com`).
3. **DNS works.** Point a device at the Pi and confirm its lookups appear on the dashboard, through the relay.
4. **Re-run to update.** Make a rule on the dashboard, then run the same line again (a fresh code, or none). Confirm it finishes, that the rule is still there, that the Pi is still paired, and that no `/opt/quietnet.new.*` folder is left behind.
5. **No terminal.** Run `curl -fsSL …/install.sh | sh` from a script with no terminal (for example through `ssh pi@host 'curl … | sh'` without `-t`) on a Pi without Docker, and confirm it stops and says to add `--yes`, having changed nothing.
6. **Uninstall.** Run it with `--uninstall`. Confirm the container and `/opt/quietnet` are gone, the volume is still listed, and the message says how to delete the volume and undo the forwarding, `quietnet-forward` and systemd-resolved files. Run the install again and confirm the rule from step 4 is back.
7. **Next to a hand-started copy.** Start QuietNet by hand with `docker compose up -d` from a folder not called `QuietNet`, then run the installer: it should stop, naming that folder, and change nothing. Then remove it and start a container called `quietnet` with plain `docker run --name quietnet ...` (no Compose): the installer should stop and suggest `sudo docker rm -f quietnet`, and `--uninstall` should leave it alone with a warning.
8. **sudo.** As a user who is not allowed to use sudo, run the line: it should stop at once, after sudo's own refusal, saying administrator rights could not be obtained. As a user whose sudo needs a password, run it over `ssh pi@host 'curl … | sh'` without `-t`: it should stop the same way and suggest `ssh -t`; with `-t` it should ask for the password and carry on.
