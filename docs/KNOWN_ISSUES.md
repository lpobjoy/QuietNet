## Open: needs testing on a real Pi

### 4. With Docker installed, an enforced device may lose all internet

Docker sets the host's rule for forwarded traffic to "drop unless allowed". An accept in the enforcer's own table does not override a drop in another, so a steered device would be cut off completely.

**Now handled (22 November):** before steering, the enforcer asks every firewall tool present whether another firewall would drop passed-on traffic. If one would, it does not steer, and the device page says what to run on the Pi. Once that accept is in place the check clears and steering starts.

Since the fourth review, each firewall table is judged on its own: an accept in Docker's table no longer hides a reject in firewalld's, because in the kernel each table decides separately. Every table in the way is named, each with a command that suits it: `sudo iptables -I DOCKER-USER -i eth0 -o eth0 -j ACCEPT` for Docker's, `sudo iptables -I FORWARD …` for a rule made with `iptables` without Docker (ufw, for example), and `sudo nft insert rule <family> <table> <chain> iifname eth0 oifname eth0 accept` for anything else, such as firewalld. These commands last until the firewall is reloaded: firewalld drops them on a reload and ufw on a restart, so on those hosts the owner needs to make the rule permanent in that firewall's own settings. This was confirmed in a two-container test with a Docker-style "drop" rule loaded: refused with the advice shown; the advice followed; steering started within 30 seconds and the device kept its internet. The enforcer does not add the accept itself, since that changes the owner's firewall.

**Docker's rule now lasts (23 November):** a command run by hand is lost when the Pi restarts, which the owner found on a real Pi (64-bit Raspberry Pi OS on Wi-Fi, `wlan0`): after a restart the device page asked for `sudo iptables -I DOCKER-USER -i wlan0 -o wlan0 -j ACCEPT` again. The installer now offers to add a small systemd service, `quietnet-forward`, that puts this one rule back every time Docker starts, for the connection the Pi reaches its router on (see [Architecture](ARCHITECTURE.md), the installer's step 10). The device page's advice says the command lasts until a restart and that re-running the installer makes the Docker part permanent. firewalld and ufw still need the rule added in their own settings.

**Shown on the home page (23 November):** the advice used to appear only on an enforced device's own page, so an owner who never opened it saw nothing wrong. When another firewall stops all steering, the home page now says "Cut live connections" is not working for any device, names the firewall, gives the command, says it lasts until the next restart and, for Docker's firewall, that re-running the install command sets it up permanently (`firewall` in `GET /api/enforcer`).

**Still to check on a real Pi with Docker:** that the check spots Docker's real rules there, and that the advice clears it. With Docker and firewalld together: that steering stays refused until both commands have been run, then starts; and that the `nft insert` command works against a real firewalld table. For `quietnet-forward`: that on a real Pi it is started after Docker, that the check clears straight after the install and again after a restart, and that `sudo systemctl restart docker` brings the rule back. If the Pi later moves to another connection (from Wi-Fi to a cable), the service still names the old one until the installer is run again. For the home-page notice: after a restart without `quietnet-forward` (or with the `DOCKER-USER` rule removed), the home page should show the notice with `sudo iptables -I DOCKER-USER -i wlan0 -o wlan0 -j ACCEPT` and the re-run-the-installer line, and it should clear within about 30 seconds of running the command.

### 45. The kill switch can let a little traffic through at first

In the two-container test, a steered device that was already settled sometimes got about one to three seconds of traffic through just after the kill switch was turned on. After that, nothing got through in 60 to 100 seconds of trying. The DNS block applies at once, so this only affects connections that were already open.

**Still to check on a real Pi:** how long the gap is with real devices (phones and TVs answer ARP differently from Linux). It is not being tuned further for now.

### 78. Home-network names sent to the router

Since the fourth review, names such as `printer.lan` or `nas.home`, and reverse lookups of home addresses, go to the home router instead of 1.1.1.1 (fixed issue 48). On 23 November the two gaps left in the code were closed:

- Single-word names (a plain `nas`, with no ending) now go to the home router too, or get "no such name" if the router isn't known. They never go to the public servers. The exception is a question about a single word with one of the record types used to check DNS signatures (NS, SOA, DS, RRSIG, NSEC, DNSKEY, NSEC3): that is a device checking signatures asking about a top-level name such as `com`, and it goes to the internet as before. Answering it "no such name" would make that device reject every `.com` name.
- If the same question (name and type) arrives while QuietNet is still waiting on the router for it, the answer is "server failure" rather than a second ask, so a router set up to send its lookups back to QuietNet can't make the two ask each other for ever. Two devices asking for the very same home name at the very same moment also get "server failure"; they simply ask again.

**Still to check on a real Pi:** that home names, single-word names included, resolve through a real router, and that the router's device names (one of the sources in issue 89) work when the Pi uses itself for DNS.

### 89. Device names: what still can't be named, and what the Pi now sends

Since 23 November QuietNet asks devices for their own names over DHCP, Bonjour, the Windows network, UPnP and the router (ARCHITECTURE.md, "Device names"). Written and tested with stand-ins only; not yet run on a real Pi or home network.

**What this means for the network.** The Pi now listens on UDP 5353 (the Bonjour group address only) and reads a copy of the DHCP requests arriving for UDP 67 (through a packet filter, without taking the port and never answering), and every two minutes sends a Bonjour question to the group and to each device, a NetBIOS question to each device, one UPnP call to the UPnP group, and short HTTP requests to devices' own UPnP description addresses. These are small and ordinary, but they are new: a household with network monitoring will see them.

**What still can't be named, and why:**
- Phones and tablets with a private Wi-Fi address that send no name when joining, don't answer Bonjour while asleep, and aren't known to the router. Many Android phones fall here. They get the "private Wi-Fi address" note instead.
- DHCP names are heard only when a device joins or rejoins the network while QuietNet is running: switching on, a computer restarting, a phone reconnecting to Wi-Fi. A device that stays connected only renews its lease, and renewals go straight to the router, so they are not heard. A Windows PC or smart TV on a cable that is never restarted may never give a DHCP name. Heard only on the Pi (Linux), through a packet filter that needs the container's NET_RAW permission; on a Mac only if run with admin rights and port 67 is free.
- On a Mac, the DHCP listener binds the broadcast address on port 67. A DHCP server started on the same Mac afterwards may find the port taken. On the Pi this does not happen: there the listener never takes the port, so dnsmasq or a hotspot can start before or after QuietNet.
- Bonjour answers are believed only from the device they are about. A Mac that is asleep, whose Bonjour Sleep Proxy (often an Apple TV or AirPort) answers for it, is named only once it wakes. This is deliberate: any device could otherwise answer for another and give it a misleading name.
- A Bonjour announcement heard from an address before QuietNet has seen which device holds it is tied to the device holding it at the next round, up to two minutes later. If the address passes to another device inside those two minutes, the announcement could be shown for the wrong device until it ages out (6 hours) or that device is named.
- Smart plugs, cameras and other small devices that speak none of these. No hardware-maker table is used, by choice.
- Devices on another network segment or behind a mesh node that doesn't pass multicast on.
- On a Mac, the Bonjour listener may share port 5353 with the system or be refused; asking devices directly still works.

**Still to check on a real Pi:** that the log shows no "Device names: not listening" line on a plain Raspberry Pi OS with avahi running (or, if it does, that avahi keeps working: `avahi-browse -a` still lists devices); that iPhones, Macs, a Windows PC, a smart TV and the router each get a suggestion; that the round never takes much more than 5 seconds (`docker logs` stays quiet; the dashboard stays quick); that nothing is ever sent from port 67 (`sudo tcpdump -ni eth0 udp port 67 or udp port 68` shows only the router and devices); that a DHCP server started on the Pi after QuietNet still starts.

### 86. The installer runs whatever is on GitHub's main branch, unsigned

The one line fetches `install.sh` from GitHub's `main` branch, and the installer downloads QuietNet from `main` (or `--ref`). Both go over HTTPS, but nothing checks a signature or a known checksum. So anyone who can push to `main` on GitHub, or who takes over the GitHub account, controls what every newly installed or updated Pi runs, as root and with network rights. The relay's install line shows `main` too, unless the relay owner sets `QUIETNET_INSTALL_URL`.

**Possible fixes:** protect `main` (required reviews, no direct pushes) and turn on two-factor sign-in for the account; publish tagged releases and have the relay's line and the installer use a tag rather than `main`; or sign releases and check the signature (hard with the standard library and plain `sh` alone). Until then, a cautious owner can read `install.sh` before running it, or pin `--ref` to a tag they have checked.

### 87. The installer depends on get.docker.com

When Docker is missing (and the person agrees), the installer downloads `https://get.docker.com` and runs it as root. That is Docker's own published script, but QuietNet does not control it: if it changes, breaks, drops a system (as with 32-bit Arm), or is tampered with, the install fails or runs something unexpected. Nothing checks it either. People who would rather not can install Docker themselves first (from their system's packages or Docker's instructions), and the installer then skips this step.

### 88. Pairing again with the installer, and the code kept by Docker

- `--relay` and `--code` on a re-run pair only a Pi that isn't paired yet. `cloud_agent.py` ignores `QUIETNET_CLOUD` and `QUIETNET_PAIR` once it holds a key, so the installer can't move a paired Pi to a new relay or account; that still needs **Unlink** on the Pi's Remote access card first. The installer's closing message says so.
- The pairing code is never written to a file, but Docker keeps it in the container's settings (`docker inspect quietnet` shows `QUIETNET_PAIR`) until the next run without `--code`. It has already been used or has expired by then, so it is of no use to anyone, but it is visible.
- Uninstalling says how to remove the systemd-resolved settings file, but does not point `/etc/resolv.conf` back at `stub-resolv.conf`. Lookups keep working either way.

### 94. Licences on the relay: what the first phase leaves out

The relay now keeps a licence per account and can enforce it (`QUIETNET_LICENCE_GATE`, off by default). Gaps left on purpose, or found while building it:

- **No way to pay or renew yet.** The paused page has no Renew button and the Licence card no billing buttons; licences come only from the owner's command line until payments are added. The wording still says "Renew at q3n.net", as the design asks.
- **"Blocking is paused for an hour", not "until 14:35".** The relay doesn't know the Pi's time zone, so the result page after the second rescue button gives no clock time.
- **Downloads don't take seats yet.** Seats in use are only the account's paired Pis. Installs that downloaded but never paired, and the 60-day expiry of seats, come with downloads.
- **The gate's "once an hour" is kept in memory.** After a restart the same would-be refusal can be logged again straight away. `licence_log` keeps the newest 1000 lines per account that the account itself caused (gate notes, at most one an hour for each kind of refusal, and rescues, at most 20 an hour); the owner's own lines are always kept, so the oldest gate notes and rescues of a busy account are dropped.
- **Waiting Pis beyond the free seats still get codes.** While the licence allows pairing and paired Pis leave a seat free, the home page gives every waiting Pi a fresh code, even when there are more waiting Pis than free seats (they can be left from before the gate was on). Pairing them stops at the seats: the first to pair take the free seats and the rest are refused with the seats sentence.
- **The legacy licences end 90 days after the first start.** Grant the owner's own account `--plan owner` (no end) before switching the gate on, or its Pis will pause when the legacy licence ends.
- **The Pi's side isn't built yet.** Pis before 0.6 ignore the licence in poll answers and send no install id or agent header, so they get the older rescue call (kill switch off only) and every copy of them pairs as a separate Pi.

### 99. "Cut live connections" and the Pi's neighbour table

Since 24 November the enforcer steers a device wherever the Pi's neighbour table lists the device's own hardware address at the address its rules are held at, whether that entry reads fresh or stale (see Fixed, and `docs/ARCHITECTURE.md`, "The enforcer"). This rests on how Linux keeps that table, and none of it has been watched on a real Pi:

- **A steered device's entry is expected to read `STALE` most of the time,** fresh only for about half a minute after QuietNet answers one of its lookups or the name finder questions it. If a real Pi behaves differently (the entry is dropped altogether while the device is busy, say), the device would leave the plan and be handed back to the router until its next lookup. Manual step 47 checks exactly this: a steered TV on one long video for ten minutes must stay steered.
- **When another device takes the address, Linux is expected to rewrite the entry** as soon as that device announces itself or speaks to the Pi, which takes the address out of the plan. Until it does, the Pi goes on sending the steering message to the old hardware address, which reaches nobody else, and the drop rules for the address apply only to traffic that comes through the Pi, which the new device's does not. So the worst expected is a few wasted messages. Manual step 44.
- **A device that has really left stays in the plan while its stale entry stays in the table,** as it did before the device tables. Nothing is sent to anyone else.
- **A device behind a Wi-Fi range extender that hides its hardware address is steered only while its entry is fresh.** One hardware address answers for several devices there, so a stale entry says nothing about which device has the number. Its "Cut live connections" can therefore lapse between its lookups: handed back to the router about half a minute after its last lookup, and steered again at the next one or at the next name round (two minutes), so a bedtime that starts in between cuts its open connections late. Its lookups are blocked throughout. Keeping such an entry fresh (a question to the device from the Pi every few seconds) would close this; it is not done, because it has not been tried against a real extender.

## Open: design decisions for the owner

### 5. IPv6: the enforcer, and devices known by two addresses

On 23 November the DNS half was fixed: the filter now also listens on IPv6 (`::`, same port, UDP and TCP), so a device given an IPv6 DNS server by the router is filtered too. If the computer has no IPv6, or the port can't be opened, it says so and carries on with IPv4. An IPv4 device reaching it over IPv6 (`::ffff:192.168.1.23`) is filed under its IPv4 address. What remains:

- **The enforcer steers and drops IPv4 only (eased 23 November).** On a BT Smart Hub, which hands out IPv6 as it ships, most streams and app connections went over IPv6, so bedtime or the kill switch left them running though the README promised an instant cut. A device with "Cut live connections" on now gets "no records" for IPv6 address lookups (AAAA) and for HTTPS and SVCB lookups (which can carry IPv6 hints), so its apps connect over IPv4 through the Pi; other devices are unaffected. What remains: a connection it already had over IPv6 is not cut and may carry on until the app reconnects; an app that has an IPv6 address from before, or hard-coded, can still use it; and an app using its own DNS can still get IPv6 addresses. The device page says so when the network has IPv6. Since 24 November an optional setting, "Take IPv6 away from steered devices" (off unless switched on), steers IPv6 as well, claiming the hub's IPv6 address to steered devices with neighbour advertisements in place of ARP. It is built but has not run on a real Pi; see issue 101.
- **A device asking from a real IPv6 address gets its own rules** (24 November: by its device, known by hardware address from the IPv6 neighbour table, whether or not QuietNet has ever seen it over IPv4; before that it was matched to an IPv4 address, and a device never seen over IPv4 could not be matched at all). The table is looked at again every minute, and at once when a lookup comes from an address not matched yet (the lookup waits up to 0.4 seconds for that look). If it still can't be matched (a new temporary address in its first seconds, or an address behind a Wi-Fi range extender) and any device is treated differently from the whole house, the answer is "refused". "Treated differently" counts an internet switch, a blocked service or a schedule for a device or group, "Cut live connections" on for any device, and any device in a group, even a group with no rules. A refused device tries its next DNS server. That may be QuietNet's IPv4 address, or the router's own IPv6 DNS server, which is a way round QuietNet, not an outage; it is not established which devices do which. With nothing of the kind set, an unmatched lookup is answered under the whole house's rules; if its IPv6 address looks built from a known device's hardware address the card says "Probably the same device as ...", as a hint only. Before this was fixed (23 November), the IPv6 listener was a way round device rules: a child's phone asking from its IPv6 address got real answers during its group's bedtime.
- **The router's own IPv6 DNS server (fixed in part, 23 November).** A router that hands out IPv6 (a BT Smart Hub does as it ships) also tells devices to use its own IPv6 DNS server. Windows and Android set up by hand for IPv4 only kept using it as well, so blocks and bedtime applied only some of the time while the device still showed lookups. "Set up a device" now gives the Pi's IPv6 address for each kind of device, or, if the Pi has none, says to switch IPv6 off on the router (BT Smart Hub: Advanced settings, IPv6). QuietNet listens for the router's announcements and the dashboard warns when they name a DNS server that is not the Pi. What remains: Android may keep the router's IPv6 DNS server even with the Pi's typed in, so there the sure fix is switching IPv6 off on the router; servers handed out by DHCPv6 alone are not seen; the IPv6 address given changes if the internet provider changes the home network's public range and the Pi has no unique-local address.
- On the Pi, matching needs the `ip` tool (`iproute2`, now in the image). Without it nothing is matched, so while any device is treated differently every IPv6 lookup from a real IPv6 address is refused. Since 24 November the home page says so ("QuietNet can't tell which device a lookup over IPv6 came from") rather than refusing with no explanation.
- **A device known by two addresses is one device (24 November).** Its history, and since the third part of the design its name, group and rules, are held against the device, by hardware address, whatever IPv4 or IPv6 address it has, and `GET /api/devices` lists one entry per device (the TV at `.65` and `.67` is one). See issues 97 and 98 for what is left open.
- **Switching IPv6 off on the router is the only fix for every device** (design, 24 November). "Set up a device" now has the steps for a BT Smart Hub (Allocation Mode off, or ULA on where there is no off switch) with what to do afterwards, and confirms "IPv6 is off on your hub" only after a full hour of listening with nothing heard. Whether a given hub offers the off switch is reported both ways by BT users; see issue 96.
- **A trial lets the Pi announce itself as an IPv6 DNS server beside the hub (24 November).** Off unless switched on. It cannot replace the hub's own announcement, so it does not close this; see issue 102.

### 93. Ways a device can still get round QuietNet

The robustness review's fixes (see Fixed) close the easy ways round, but not all of them. Each needs either a change on the device, a router that can block them, or a much bigger change to QuietNet:

- **Devices without "Cut live connections" can still use another DNS server by its address.** A phone or TV set by hand to 8.8.8.8 (or the router's address) sends its lookups straight there. The redirect works only for devices steered through the Pi. The BT Smart Hub cannot block outgoing DNS itself. Turning on "Cut live connections" for the device closes it.
- **Secure DNS set up by address alone, or with a service not on the list.** A browser told to use `https://1.1.1.1/dns-query` uses the ordinary web port and never looks a name up, so neither the name block nor the port 853 drop stops it. Services not in `OTHER_DNS_SERVICES` are not blocked; add them there.
- **A VPN, or an app with its own built-in DNS,** gets round all of it, steered or not. QuietNet sees only that the device went quiet.
- **IPv6.** The redirect and the port 853 drop cover IPv4 only, like the rest of the enforcer. A steered device gets no IPv6 addresses from QuietNet, but a connection it opened over IPv6 before "Cut live connections" was switched on (or before bedtime began) is not cut and may carry on until the app reconnects; an app that remembers an IPv6 address, or uses its own DNS, can still reach it over IPv6. An Android phone lists the router's IPv6 DNS server first, so a phone pointed at the Pi by IPv4 DNS alone sends most of its lookups to the router, and may keep doing so even with the Pi's IPv6 address typed in (issue 5). This goes for steered devices too: their lookups to the router's IPv6 DNS server never pass through the Pi. So since 24 November, while the home network has IPv6, every device that uses QuietNet is marked "Can bypass over IPv6" on the Devices page and its own page, steered or not, and the "Cut live connections" card says it covers IPv4 only. The optional "Give no device IPv6 addresses" switch narrows this for lookups that do reach QuietNet. The optional "Take IPv6 away from steered devices" setting (option c2, off by default, built but not yet tested on a Pi: issue 101) closes it for the devices "Cut live connections" is on for, by claiming the hub's IPv6 address to them. Switching IPv6 off on the router closes all of these.
- **With `iptables` in place of `nft`,** ordinary DNS to another server is not redirected (port 853 is still dropped). The Pi image always has `nft`.
- **Lookups already on their way to 8.8.8.8** when steering starts are not redirected until they time out, as is normal for this kind of redirect.
- **A device with no rules of its own can use another DNS service** (Private DNS, secure DNS) unless the home-page switch "Stop every device using another DNS service" is on. Off by default, because a device set to use one strictly loses all names when it is blocked.
- **The "tried to use another DNS service" flag is kept in memory**, so it is lost when QuietNet restarts; the device's history still shows the lookups.
- **A device that changes both its private Wi-Fi address and its number at once** looks brand new, so it has none of its old rules: only the new-device group covers it, and the home page suggests "It may be the same device". Nothing is merged automatically (the owner's choice). Saying yes joins the two into one device, with one history and every rule either had.
- **A visitor given the number a child's phone had, with a private Wi-Fi address of its own,** is held to the child's rules until the owner answers "Is it the same device?". This errs towards keeping the rules; answering "No" ends it, and it ends by itself when the child's phone is seen again. Since 24 November the rules go with the visitor's device to any other number while the question is open.
- **Behind a Wi-Fi range extender that shows every device with its own hardware address,** QuietNet knows a device only by its number: its rules stay with the number and can't follow it. Until the extender has been seen at two addresses at once on three looks, the second address gets no rules at all (it may be another device), and the first is treated as one device. A device with rules that starts connecting through an extender keeps them at that number, but "Cut live connections" does not steer it there, and its lookups over IPv6 can't be matched (refused while any device is treated differently).

### 96. IPv6 honesty and small fixes: what the first part of the IPv6 design leaves open

The first part of the design for IPv6, DNS and device identity (24 November) fixed the smaller faults and made the dashboard honest about IPv6. It does not close the IPv6 gap; only switching IPv6 off on the router does, or the later parts of the design. Left open, or not confirmed:

- **The BT Smart Hub steps are from users' reports, not from a hub.** "Set up a device" says Advanced Settings, IPv6, Configuration, Allocation Mode "Off", and "ULA Enabled". BT publishes nothing on this for home hubs, some firmware is reported to lack the off switch, and the words on the page may differ. Check on the owner's hub (manual step 18) and correct the wording.
- **"IPv6 is off on your hub" can take longer than an hour.** It also needs the Pi to have lost its own public IPv6 address, which the Pi keeps until the address runs out or its network connection restarts; how long that is on BT is not known. It is never shown early: a restart of QuietNet starts the hour again, and where the listener can't run the page says it can't tell. If the announcement listener stops (its socket fails), it is not started again until QuietNet restarts, and the confirmation stays off.
- **A Pi with its own IPv6 switched off cannot check, and says so.** With IPv6 disabled on the Pi's home network card (`net.ipv6.conf.wlan0.disable_ipv6=1`, the same for `all`, or NetworkManager's "IPv6: disabled"), the Pi hears no announcements whatever the hub does. "Set up a device" then says QuietNet can't tell whether IPv6 is on, and `ipv6.can_hear` is `false`; the confirmation never appears. Devices are not marked "Can bypass over IPv6" in that state either, because QuietNet cannot know: the page says so, but the Devices page alone does not. That Linux drops every IPv6 message on such a card before a listening program sees it is from the Linux source, not from a Pi (manual step 28). The check looks at the card the Pi's default route uses; a Pi with two cards on the home network, with IPv6 off on only the other one, is not covered.
- **What a BT Smart Hub announces with Allocation Mode off and "ULA Enabled" on is not known.** A router with no IPv6 internet but a private range should announce with a router lifetime of 0 and may still name itself as IPv6 DNS server. If the hub does, devices keep using that server; the confirmation then stays off, devices stay marked, and the page says something still names an IPv6 DNS server and suggests turning ULA Enabled off too. That advice is a guess until checked on the hub (manual step 27). A Thread border router that names a DNS server of its own would hold the confirmation back the same way; none is known to.
- **A steered device is marked "Can bypass over IPv6" too.** Steering covers IPv4 only unless the optional "Take IPv6 away from steered devices" setting is on (issue 101). Even with it on the label stays for now: that setting has not run on a real Pi, and the label should come off a device only once it is known to work there.
- **The quick look may be a moment too early.** It reads the Pi's IPv6 neighbour list when the lookup arrives. If the Pi only learns the device's hardware address when it sends its reply, the first lookup from a new address is still unmatched (refused while any device is treated differently, otherwise filed under the IPv6 address), and the second, a few seconds later, is matched. Needs a real phone (manual step 20).
- **Unmatched lookups are refused in more homes.** Any home with a device in a group, or with "Cut live connections" on, now refuses IPv6 lookups it can't match; before, only homes with a device or group rule did. The owner chose to keep refusing: answering would let a device with rules through under the whole house's rules. A refused device tries its next DNS server.
- **One hardware address at two numbers at once** (a Wi-Fi range extender): since rules are held against the device (issue 98), an IPv6 address whose hardware address is an extender's, is at two live numbers at that look, or is listed in the IPv6 neighbour table with more than one link-local address (each device has only one, so two are the sign of an extender not yet recognised), is matched to no device and gets no device's rules, so it is refused while any device is treated differently and otherwise answered under the whole house's rules. An extender never seen at two live numbers at once, behind which only one device has ever spoken to the Pi over IPv6, is not caught by any of these: that one link-local address is taken for the known device (issue 102 says what follows). It still keeps a share of the listeners of its own, so one busy device behind the extender can't have the others' lookups dropped, but only once the hardware address has been seen shared often enough to count as an extender (three looks) or is listed with more than one link-local address; until then they share one. The IPv6 DNS announcement trial, which would invite every device behind an extender to ask QuietNet over IPv6, holds back while an extender is known, and while one hardware address has more than one link-local address (issue 102).
- **The hub's link-local and hardware addresses are kept as heard.** Anyone on the home network can send a router announcement, so `ipv6.routers` may list a second "router". The optional IPv6 steering (issue 101) goes by this list, taking the real router heard most recently as the hub; it does not yet check that router against the home router's IPv4 hardware address, which the device tables now hold.
- **"Give no device IPv6 addresses" has not been tried with real devices.** It is off unless switched on. A service that works over IPv6 alone would stop working while it is on. It does not apply to names QuietNet doesn't check (reverse lookups, names with unusual characters), which go to the internet as before.
- **Each device's share of the listeners is now one across IPv4 and IPv6,** but the house-wide limits (256 lookups, 64 TCP connections) are still counted on each listener separately, and an IPv6 address that can't be matched, or that sits behind a range extender, has a share of its own.

### 97. The device tables: what the second part of the IPv6 design leaves open

The second part of the design for IPv6, DNS and device identity (24 November) makes the hardware address the identity of a device for its **history**: new `device`, `device_hw` and `address_use` tables, each lookup filed against the device that made it, one entry per device in `GET /api/devices`, and a one-off move of an older household's database. Left open on purpose, not confirmed, or found while building it:

- **Rules, names and groups were still kept under IPv4 addresses** when this part was built. The third part holds them against the device: see Fixed, and issue 98 for what that leaves open.
- **The dashboard page still shows each card by its address.** It passes the device's number with every change, for the activity list and for "Forget this device's history". A page from before this change (an older relay serving a newer Pi) passes no number, so there a card's activity list and its "forget" cover only what was recorded under the card's address, while its counts cover the whole device; its changes reach the device listed under the card's address. A device that has left, and whose address has since gone to another device, has no address of its own: it is in `GET /api/devices?all=1` (`"ip": ""`) with its history, name and rules, but the page shows no card for it until the page is changed to list by device (issue 98). (Without `all=1` it is left out, so that a page from before the device tables, which an older relay may still serve, is not handed a card it cannot open.) **Since the fourth part (issue 100) the page shows one card per device, known by the device's number, and a device with no address of its own has a card too.** What this bullet says still holds for an older page served by an older relay.
- **The move has only been run on made-up databases.** On a Mac a two-million-row history (the most QuietNet keeps) moves in about a second and its older rows are filed in about four; a Pi's SD card will be many times slower. While the one transaction runs, the database lock is held: lookups are answered and blocked as usual, but the dashboard, rule changes, the history writer (whose queue has no limit, so nothing is lost) and the enforcer's two-second tick all wait until it finishes. A steered device whose tick is late can slip back to the real router for those seconds; its lookups are still filtered, and it is steered again when the tick resumes. If the Pi is stopped in those seconds, the enforcer's clean-up waits for the lock (up to 15 seconds); whatever it leaves is undone at the next start, as after a power cut. A move is never begun once a stop has been asked for: `start_up()` then does not start the device keeper. How long this is on a real Pi is manual step 30.
- **A power cut during the move** should leave the old database untouched (the database rolls an unfinished transaction back when it is next opened), and the move then runs again from the start. Tested here only by making the move fail part-way; pulling the power is manual step 32.
- **`quietnet.db.before-devices` stays in the data folder for 30 days**, as large as the database was (up to about 250 MB). It holds the household's whole history from before the move, so QuietNet deletes it once it is 30 days old (the same limit as the history itself; looked at each hour) and at once when everyone's history is forgotten. **Forgetting one device's history does not take that device's older lookups out of the copy**: they stay in it, readable by anyone with access to the files on this computer, until the copy is deleted. Going back to an older version by the copy is therefore possible only for those 30 days, and not after everyone's history has been forgotten. It can be removed by hand sooner. Deleting it on time on a real Pi is manual step 36.
- **The move waits up to two minutes for this computer to know its own address** (a Pi can start before its Wi-Fi is connected). If no address is found in that time, the move goes ahead without one: this computer's and the router's older history is then filed under ordinary devices that have no address of their own once the real addresses are known, so the page shows it on no card (it is in `GET /api/devices?all=1` and in the whole-house figures, and ages out after 30 days). No rules are affected. The same happens if the router's address is found only after the move. Manual step 32.
- **A failed move is not tried again until QuietNet restarts,** and each try makes the copy again. Too little free space is tried again every hour.
- **Old history goes to whoever has the address now.** The old tables do not say when an address changed hands, so every older row goes to the device its address was given to in the move: the device its rules were recorded for, else (a best guess) the hardware address most recently seen there or found there by the last scan. Rows from before a change of hands sit with the wrong device until they are 30 days old. Which matches were a best guess is kept in `moved_address`, for the next part of the design to use when it moves rules.
- **The record rests on the neighbour table's freshness, which has not been watched on a real network.** An IPv4 address counts only while its entry is fresh (reachable, or being checked). The design expects an idle device's entry to become fresh within seconds of a lookup, because the Pi must reach the device to answer it, and the look every 5 seconds to catch that; if a real phone's entry stays stale, its lookups are filed under its address (an "addr" device) after 3 minutes, not against the phone. An entry being checked (`DELAY`, `PROBE`) counts as fresh although Linux has not yet confirmed it; a device that takes over an address without announcing itself could have a few seconds of lookups filed against the previous holder. On a system that gives no freshness (a Mac, or Linux without the `ip` tool), every entry counts as confirmed, so an address that changes hands is only noticed when the old entry goes, and a device that moves is not followed to its new address until the old entry has gone. Manual step 35.
- **One hardware address at two live addresses** gets no device at the second address until the first is no longer confirmed, or until it has been seen that way on three looks and counts as a range extender, when each address becomes a device of its own. There is no way yet for the owner to say "this is one device" or "these are two" (Merge and Separate come with the dashboard part). Lookups from the waiting address are filed under that address. **Merge and Separate came with the fourth part (issue 100);** they join or part devices, and do not change how one hardware address at two live numbers is treated.
- **A phone that makes itself a new private Wi-Fi address is a new device,** with a new, empty history; its old history stays with the old device, which is kept while it has a name or rules. Nothing is merged automatically (the owner's choice). The owner can say it is the same device, which joins the two histories (issue 98).
- **A lookup over IPv6 that could not be matched to a device by its own address** (behind a range extender, or while its hardware address is at two live addresses) is filed against the device of the IPv4 address it was judged under, which for an extender is one of the extender's addresses, not necessarily the right one.
- **Updating the map from DHCP requests, and pausing a device's rules on a reused address until the new holder is confirmed,** came with the third part (issue 98). For the history the safety still comes from never counting a stale entry.
- **Devices and addresses are forgotten after 30 days unseen**, and a device that comes back later is a new device with a new number. A device with a name, a group, rules or an open "same device?" question is never forgotten.
- **A flood of made-up hardware addresses** stops new devices being made once 10,000 are remembered; the hourly pass then forgets the longest unseen beyond 5,000, and a forgotten device's history rows are left filed against a number no device has (they age out). That holds with a new-device group chosen too: the group QuietNet itself gives a new device is no reason to keep it (see Fixed). Until the hourly pass has run, a real newcomer gets no device: only the whole house's rules, and not the new-device group. Lookups that can then get no device are filed against "no device" (number 0) and are not shown on any card. The move does the same with an old history that holds more than 5,000 addresses with no hardware address.
- **An older QuietNet started on a moved database** records lookups with no device. When the new version starts again, a device still at the same address and confirmed there within the first minute gets its lookups from that time; every other lookup from that time (a device that was asleep at the restart, one that changed address, one that was new) is filed under its address alone. Such an entry has no address of its own while a device holds that address, so the page shows it on no card: it is in `GET /api/devices?all=1` (`"ip": ""`) and in the whole-house figures, and ages out after 30 days. Since the third part the older version also finds no device's name, group or rules (they are no longer in the tables it reads), and what it sets is noticed and offered back afterwards: see issue 98. Going back the documented way (putting `quietnet.db.before-devices` back) avoids all of this.
- **The look every 5 seconds runs `ip -4 neigh show`** (or `arp -an` on a Mac). It should cost very little; not measured on a Pi (manual step 35).

### 98. Rules held against the device: what the third part of the IPv6 design leaves open

The third part of the design for IPv6, DNS and device identity (24 November) holds a device's name, group and rules against the device itself, known by its hardware address, and no longer under an IPv4 address: scopes are `dev:<number>`, nothing is moved when a number changes, and `S.addr_rules` says whose rules a lookup from each address gets. Left open on purpose, not confirmed, or found while building it:

- **After a restart, a device's rules apply only once QuietNet has seen it.** Whose rules an address gets comes from the neighbour table alone, never from the record of who used which address (`address_use`), and is not kept across a restart. A look is taken at once on starting, so after a restart of QuietNet alone every device still in the Pi's neighbour table is covered within a moment. After a restart of the Pi itself that table is empty: each device's first lookups, for up to about 5 seconds after it first speaks, get only the whole house's rules, and an answer given then is remembered by the device for up to two minutes. Before this part, rules were kept under addresses and applied from the first lookup. Manual step 41.
- **An idle device's rules rest on what the neighbour table last said.** An address whose entry has gone stale, or gone altogether, keeps the device last seen there until that device, or anyone else at the address, shows in the table. A device that takes the address over in between is treated as the previous device until the next look sees it (up to 5 seconds; before this part, up to a minute), unless its DHCP request was heard. If the previous device's internet was off, the newcomer's first lookups get the blocked answer, which it remembers for a minute. That a device given an address always shows in the Pi's table before its first lookup arrives is from how ARP works, not from a real network. Manual steps 38 and 39.
- **DHCP requests are heard only when a device joins or rejoins, and only where the listener runs.** Renewals go straight to the hub. The listener needs the right to read raw packets (the container has it), and is not started with `--no-device-names`. Where nothing is heard, the look every 5 seconds is what notices a change. What a real phone, TV or console puts in its request (the address asked for, or only the address it already holds), and whether the Pi hears them on BT Wi-Fi, has not been checked. Manual step 39.
- **A DHCP request for a number another device holds, forged or honest, can change that number's rules for a while.** Anyone on the home network can send one. It can't overrule what the neighbour table confirmed at the last look, can't make a device, can't steer, and lapses in two minutes. But while a device's own entry is not counted as confirmed (it has been idle for half a minute), a request naming an unknown hardware address pauses its rules on its own address, and one naming another known device gives that address that device's rules. The word stands until a look confirms someone at the address, the device that said it asks for another address or is confirmed at another address, or two minutes pass (a look follows each request by a second). An honest case: a device that rejoins asks for the number it had before; if the router has since given that number to a device that is idle, the idle device gets the asker's rules until the asker's next request (for the number it is really given, usually within a second) or the next look that sees the asker elsewhere. If the asker never appears anywhere (it asked and left), the word stands for the two minutes, and the idle device's first lookups in that time get the asker's rules, a blocked answer being remembered for a minute. Telling a request that answers the router's offer from one that only asks for an old number (the DHCP "server identifier") would close that, and is not done yet. A device that forges requests over and over could get some lookups answered under the whole house's rules; a device able to do that can also change its hardware address, which makes it a new device, and the new-device group is the cover for both. It cannot use this to slip out of "Cut live connections": steering takes no notice of DHCP requests. The other side of withdrawing a word when its device is confirmed elsewhere: a device that really does change number while the Pi still counts its old entry as confirmed (within about a minute of its last answered lookup there) loses its word at the next look, and its lookups from the new number get only the whole house's rules until the old entry lapses, as for any hardware address at two live numbers. Manual step 48.
- **A device with rules that has left, and whose number has gone to another device, has no card on the page.** Its name and rules are kept under its number and apply the moment it is back; it is in `GET /api/devices?all=1` and its schedules show on the Schedules page as "A device that is not on your network now"; but until the page lists by device (the next part) its rules can't be seen or changed from a card. They affect no other device. They do count towards "some device is treated differently", which keeps unmatched IPv6 lookups refused (issue 5). **Closed by the fourth part:** the page now lists such a device as a card of its own, "Not on your network now" (see Fixed).
- **Joining two devices can't be undone yet.** "Yes, it's the same device" joins them for good: one name, one group, every switch, block and schedule either had, one history. Where both had a name or were in a group, one gives way; the group kept is that of the device the rules belong to, and the recent changes say which group the device left, but the owner has to put it back by hand if that was wrong. "Separate" comes with the dashboard part, as does a general "Merge" that shows what would apply afterwards; until then joining is offered only where QuietNet asks, and refused when the newcomer has rules of its own that were not already being combined. **Closed by the fourth part:** "Separate" takes a hardware address out again, and "Merge with" shows what would apply first (see Fixed, and issue 100 for what is left), except a merge with an entry known only by its number, which Separate can't undo (issue 100).
- **A newcomer is asked about only when it takes a number straight from the device with rules,** as the looks at the neighbour table saw it. A phone that forgets the network while QuietNet is restarting is therefore not held at the first look afterwards (what the looks knew is not kept across a restart, and the record of who used which address is deliberately not used: it reaches back a month). It then shows only as a suggestion ("It may be the same device"), with nothing applied; the new-device group covers it meanwhile. A follow that had already started survives a restart. Nor is it held while the earlier device's hardware address is still listed at another number, even on an old stale entry: QuietNet can't tell a device that has moved there and gone idle from an entry Linux has simply not cleared (on a small network it keeps them for a long time), and holding a stranger's phone to a child's rules is the worse mistake. So a phone that changed number at some time, and then forgets the network, can come back at its present number with a new private Wi-Fi address and not be held; the home page suggests it may be the same device once the old one has been unseen for 15 minutes. The version before this part behaved the same way here. Manual step 42.
- **A newcomer held to another device's rules** gets them as well as its own, wherever it goes, until the owner answers, the first device is seen again beside it, or the first device's name and rules are all removed. A second new private Wi-Fi address at the same number, before the owner has answered about the first, is held to the same rules and asked about too (unless the first newcomer is still listed at another number). A visitor's phone with a private Wi-Fi address that is given a child's old number is therefore restricted until then (issue 93). The switches on its own card show what applies to it; switching one off there does not lift what reaches it from the other device, which only answering the question does. Its controls say where each comes from.
- **Rules held against a number.** A rule set for an address before QuietNet could tell which device has it, or left with a number by the move, applies to lookups from that number, and a device seen there is given them (as well as its own) and the owner asked. While the question is open they go with that device to any other number. After "no" they stay with the number, and each new device seen there is asked about in turn.
- **Devices behind a Wi-Fi range extender.** A device with rules that starts connecting through one keeps them at its number (the number's own device stands in for it) until it is seen away from the extender, but "Cut live connections" does not steer it there (before this part it was not steered there either), and such a number can't be joined to a device, whether or not the extender is listed at the moment the owner asks (QuietNet remembers which numbers an extender answers for: see Fixed). A number behind an extender with its own "Cut live connections" switch on is steered only while its entry in the Pi's neighbour table is fresh (issue 99). A device first shown behind an extender is no longer put in the new-device group: when an extender is first recognised, every device behind it becomes "new" at once, and they must not all be restricted by accident. Whether BT discs show devices this way is still not known (manual step 40).
- **The move of rules has only been run on made-up databases.** For a device that had rules under two numbers, the older QuietNet applied the set kept under the number the device was *not* at. The move keeps that set with the device, going by where the old record last has the device, and sets every other set aside for the owner, applying to nobody until the owner chooses; so the device has the rules it had the day before. Only when the old record does not put the device at either number is the choice a guess (the first in order is kept, and the notice says so). A set that is set aside no longer applies to a lookup from its number by a device QuietNet can't identify (after a restart, before the first look), as it did before the move. A name alone goes to a device on a best guess. Manual step 43.
- **While the move has not been done** (in the minutes after the first start of this version, for as long as there is too little free space, or after it failed), rules are still kept under numbers and no longer follow a device to a new number at all: only the pause on a number a different device has is kept. So in that state a device that the older QuietNet was giving the rules kept under its *other* number (the "rules kept there apply to it instead" warning) gets the rules kept under the number it has instead; the move puts that right when it runs. No device is put in the new-device group and no "same device?" question is asked in that state. The paused card's "It's the same device" button still works there (it makes the rules under the number apply to the device that has it now); every other "same device" answer is refused, saying whether QuietNet is waiting for free space or needs a restart. The home page says so.
- **A database with the device tables for its history but its rules still under addresses** (version 1: only ever made by this branch before this part) gets the second half of the move. Tested on a made-up database only.
- **An older QuietNet started on the upgraded data finds no device's name, group or rules,** because the move emptied the tables it reads: every device then gets only the whole house's rules (no device is in a group there either). That is fail-open, and is why the README says to put the kept copy back first. What the older version sets meanwhile is noticed when this version starts again and offered back ("Bring them in"); it is not brought in unasked, and until it is, those rules are not in force.
- **A named device is never forgotten,** nor one with a group or rules, and they do not count towards the 5,000-device limit. A household that names very many devices keeps them all; nothing caps that.
- **An older dashboard page** (an older relay serving a newer Pi) names devices by address. The Pi takes that to mean the device listed under the address at that moment; if the address changes hands between the page being drawn and the button being pressed, the change lands on the new holder. The page shipped with this part sends the device's number, which can't go astray.
- **The tables are not named as the design names them.** The design asks for `device_group(device, gid)` and `enforced(device, mac)`. Tables of those names already exist with other columns and are still read on an older database, so the new ones are `group_member` and `live_cut`.
- **One hardware address at two live numbers** gets rules at the first only; there is still no way for the owner to say "this is one device" (issue 97). (Merge and Separate, added by the fourth part, are about two hardware addresses being one device, not about one hardware address at two numbers.)

### 100. One card per device, Merge and Separate: what the fourth part of the IPv6 design leaves open

The fourth part of the design for IPv6, DNS and device identity (24 November) gives the dashboard one card per device, an address list on the device's page, pickers by device name, and "Merge with" and "Separate", each shown to the owner before it is done. Left open on purpose, not confirmed, or found while building it:

- **Not tried with real devices.** The two cases the design names, a laptop on cable and Wi-Fi and a phone with a new private Wi-Fi address, have only been run on made-up neighbour tables. Manual steps 49 to 60.
- **A merged device at two numbers at once** (cable and Wi-Fi both connected) is steered at each when "Cut live connections" is on, and both numbers get its rules. Whether a real laptop keeps both connections up, and which one it uses for DNS, has not been watched.
- **"Is it the same device?" knows a device by one presence, not by each hardware address.** The third part's rule is: a newcomer is held to a device's rules only while that device is nowhere on the network, and the hold ends when the device is seen beside the newcomer. For a merged device that means any of its hardware addresses. So when a merged laptop is on its cable and its Wi-Fi comes back with a new private address, the new address is not held to the laptop's rules and no question is asked: it is a new device (in the new-device group if one is chosen) until the owner merges it by hand. That errs towards not restricting. A question that was open about a device when it was merged into another is kept (it now asks about the merged device), and ends the same way.
- **Separate leaves the history where it was** (the owner's decision 6). The separated device starts with an empty history, and for its first seconds it has no card unless it was merged or separated before; it is listed straight away because the owner separated it. Lookups it made while merged can't be told apart from the other hardware address's and stay with the device it was merged into until they are 30 days old.
- **A separated device with no rules is not put in the new-device group.** "With no rules" means none: only what is set for the whole house applies to it until the owner gives it a group or rules. That is the owner's answer, shown before it is done, but a child's tablet separated that way is uncovered until then.
- **"With the same rules" copies; it does not link.** The separated device gets its own copy of the group, internet switch, blocked services, schedules and "Cut live connections". Changing one device afterwards does not change the other. The schedules are copies with the same name, so the Schedules page shows two.
- **Separated devices are remembered as different for as long as both are remembered.** If the separated one carries nothing and is unseen for 30 days it is forgotten, as any such device is; if its hardware address then comes back at the other device's old number, the "same device?" question can be asked again.
- **A preview that is out of date is refused, but two requests that arrive in the same instant are not ordered.** The check and the change are not one step: a rule changed by a second browser in the moment between them is merged as it then stands. The window is a fraction of a second, and what is merged is still the two devices the owner chose.
- **Merging a device known only by a number** gives its rules and history to the device with a hardware address. If something still looks things up from that number and QuietNet can't match it to a device, it shows as a separate entry again, with no rules. **Such a merge can't be undone with Separate**, and this is also what "Yes, they are this device's" does for rules kept under a number: the number has no hardware address to take out again, its entry is gone and its rules are the merged device's own. The preview says so before the owner confirms, in place of the usual "you can undo this with Separate", and the way back is to take the rules off the merged device by hand, one at a time. A real undo would need a record of which rules came from the number, and is not built. A number behind a Wi-Fi range extender can't be merged at all, and two entries both known only by a number can't either.
- **A number once behind a range extender stays unmergeable for up to 30 days after the extender is taken away,** until the extender's hardware address is forgotten (`KNOWN_MACS_DAYS`), unless a device known by its own hardware address is seen at that number first. QuietNet can't tell an extender that has been unplugged from one whose devices are all asleep. The owner can still set the same rules on the other device by hand.
- **Merging a held newcomer into a third device closes the question.** A newcomer being held to a phone's rules ("same device?", not answered) can be merged into some other device; the preview lists the phone's rules as stopping for it, and once confirmed they do, because the owner has said which device it is. If that was a slip, Separate afterwards does not bring the hold back: only the "it may be the same device" suggestion returns, once the phone has been unseen for 15 minutes, with nothing applied. (The other way round, a third device merged INTO the held newcomer, keeps the hold through a Separate: see Fixed.)
- **The address list on a device's page is not the whole record.** It shows the addresses the device has now or was confirmed at in the last day, 32 at most, as `GET /api/devices` gives them. An address it left more than a day ago (the TV's old `.65`) is not shown, though its history from that address is still the device's. The design's line for this page can be read as asking for the full record of addresses; showing older ones would need a call that reads the `address_use` table for one device.
- **The "Probably the same device as ..." hint on an IPv6 address listed on its own is still only a hint.** It offers no merge: an address with no device has nothing to merge until it is named, and an IPv6 address built from a hardware address proves nothing.
- **The design's stronger hints are not used.** A matching name heard over DHCP, or an iPhone's lasting IPv6 address turning up on a new hardware address, do not raise a "same device?" suggestion; the design marks both as weak or unconfirmed. The suggestions are those of the third part.
- **Through an older relay** the page may be the older one, which knows cards by address and has no Merge or Separate. A newer page on a Pi from before the device tables shows no "Merge with" (there are no device numbers). On a Pi that has device numbers but not this part (the second or third part), "Merge with" and "Separate" are shown, and pressing them says that this QuietNet needs updating and changes nothing; "same device?" is answered with the older call.
- **Cards for devices not on the network now** can add to the list in a household that names many devices that later leave. They are sorted after active devices; nothing hides them.
- **Not checked in every browser.** The preview dialog and the new parts were looked at in one browser, in the three looks and at phone width (manual step 56 asks for the rest).

### 101. Taking IPv6 away from steered devices: what is built but not yet tested on a Pi

The IPv6 steering of the design (option c2) is built, off by default behind the setting "Take IPv6 away from steered devices". The frame builders, the firewall text, the save-and-restore and the safety checks have unit tests (`tests/test_enforcer_ipv6.py`), but nothing here has run on a real Pi, real devices or a real hub. Left open, or not confirmed:

- **None of it has run on a real network.** Whether the Pi hears a device's reachability checks for the hub's address on BT Wi-Fi, whether answering them from a raw socket keeps the device steered, how the hub reacts to another device claiming its address, and how fast a device falls back to IPv4 after a clean stop, a kill, a `docker stop`, an upgrade or a power pull, are all untested. Manual steps 61 to 68 and 83 in `docs/TESTING.md` cover these; correct the code and this issue from what they find.
- **Choices the design left open, and what was picked.** The claim sets the "router" flag (the Pi stands in for the hub fully, so a device keeps sending it everything, DNS included); the design noted clearing it might speed the fall back to IPv4 but delay recovery, which needs measuring. Other IPv6 traffic is left to Linux to drop silently with forwarding off, rather than actively refused on an unused port (the design marked the active refusal uncertain and "may help"; the safest choice for a household is not to add traffic that could misbehave).
- **A device is claimed only when its lookups can be answered.** The claim is withheld (and the reason shown on the dashboard) unless the `nft` tool is present, the load has not been rejected, QuietNet is listening over IPv6, it has a lasting IPv6 address of its own (`S.v6_dns`, a ULA or public address) and the hub's IPv6 DNS address is known. So a steered device's lookups to the hub's IPv6 DNS address are never left silent; what is untested is only that the redirect works over IPv6 on a real Pi.
- **A device with its own built-in IPv6 DNS server gets no answer from it.** The IPv6 redirect catches only lookups sent to the hub's IPv6 DNS addresses (its link-local address and those its announcements name), as the design says. A steered device that sends lookups to another IPv6 DNS server (a Chromecast, Nest or Google TV using 2001:4860:4860::8888, or one typed in by hand) has them dropped with the rest of its IPv6, with no answer. Its IPv4 lookups, to 8.8.8.8 for example, are still answered by QuietNet, so it is not cut off, but it may be slow while it waits for the IPv6 server to time out. How slow is not measured (manual step 83). A choice left open for the owner: catch every IPv6 port-53 lookup from a steered device that is not addressed to this computer, as the IPv4 redirect does. That goes beyond the design and waits for the result of step 83.
- **Learning the device's link-local address.** It comes from the Pi's neighbour table or from frames the Pi hears (mDNS and group-membership reports), so a device that has never spoken IPv6 to the Pi can still be steered; this may take minutes after the setting is turned on, and a device is named in the problems meanwhile. The address the neighbour table gives comes first; one heard on the wire is used only when the table gives none. A chosen device keeps its claim at its last known address if the table loses the entry. None of this timing is measured on a Pi.
- **More than one link-local address for one hardware address means the device is left alone.** Every link-local address heard from a hardware address is kept for an hour after it was last heard, and an address that was claimed counts for an hour after its last claim. With more than one known (heard, given by the table, or last claimed) no claim is sent, a claim already made is corrected at the address it went to, and the page says more than one device seems to share the hardware address. A claim never moves from one address straight to another. What this leaves: if only the device the owner did not choose, behind an unrecognised shared hardware address, is ever heard (the chosen one silent over IPv6 and absent from the Pi's IPv6 neighbour table), that one address is taken for the chosen device and claimed, until the other speaks or the extender is recognised; nothing can tell them apart. A single device that changes its link-local address, or gives itself a second one, has its IPv6 left alone for up to an hour (so a device that adds a second link-local address on purpose gets its IPv6 back, and the page shows it). Anyone on the home network can forge a frame carrying a steered device's hardware address and so have that device's IPv6 handed back for an hour: the direction that cannot break the household's internet, but a way round this setting.
- **The hub's IPv6 address must be known first.** The claim needs the hub's link-local and hardware addresses, learned from its router announcements (`ipv6.routers`); until one is heard with a hardware address, nothing is steered. Anyone on the network can send an announcement, and `plan6` trusts the most recently heard real router without checking it against the hub's IPv4 hardware address. The device tables now hold that address (`S.hub_mac`, the fixed "hub" device), so the two can be matched; this was left undone when the parts were joined, because whether a BT Smart Hub announces IPv6 from the same hardware address it answers IPv4 from is not known (manual step 61). A second "router" that is not the hub would have its address claimed in the hub's place: the steered devices would then keep their IPv6 through the real hub, and nothing else would break.
- **The DNAT target with a link-local hub DNS server.** When the hub's IPv6 DNS server is its link-local address, the redirect sends the lookup to the Pi's lasting (ULA or public) address and relies on the kernel's connection tracking to put the hub's address back on the reply. This is the same approach as the IPv4 redirect but has not been seen working over IPv6 on a Pi.
- **Which device is steered comes from the device tables** (the second to fourth parts of the design), as for IPv4: only a device with "Cut live connections" on that the Pi's live neighbour table lists, at the number its rules are held at and with its own hardware address. No such entry, no claim; the record of who used an address is never used. A device merged from two hardware addresses is claimed at each. `plan6` goes by the neighbour table the IPv4 plan read on the tick before (up to 5 seconds old) so that `ip neigh` is not run twice a tick, and the enforcer claims only a device IPv4 steering is holding, so IPv6 follows IPv4 by one tick (about two seconds) both ways. On a database not yet moved to the device tables it goes by the number the cut is kept under, as the older version did. None of this is checked on a Pi (manual steps 44, 50 and 62).
- **Devices behind a range extender are left alone**, as the owner chose: a device known only by its number, or whose hardware address is a range extender's, is never claimed and its page says so. A hardware address at two live numbers at once (it may be an extender not yet recognised: its IPv6 addresses are matched to no device either), or with more than one link-local address (in the Pi's IPv6 neighbour table, or heard on the wire in the last hour), is treated as shared straight away and its page says more than one device seems to share it. The price is that a single device whose old link-local entry is still listed is left alone until the old entry goes.
- **A device's IPv6 steering problem is shown under the number it has now.** `ipv6_steering.problems` is keyed by IPv4 address, like the enforcer's other problems; for a merged device at two numbers at once the page shows only the one for the number on its card.
- **Recovery after a restart.** The hub's link-local and hardware addresses are saved with the steered devices, so the first tick after a restart hands each saved device back with a correction before the hub is heard again (so a steered device has its IPv6 back within a few seconds of a restart); a device still chosen is claimed again only once the hub next announces, which can be minutes. On a clean stop or setting-off the correction goes within the stop grace period. If neither the live nor the saved hub address is known, or the Pi is killed, the device is relied on to right itself once the Pi stops answering its checks; how long that takes is not measured.
- **The IPv6 reply-from-the-asked-address path** is live for every home on Linux, setting on or off, and is unproven on a real Pi until step 68 is run.
- **Stopping asks for the IPv6 plan once more, and with the setting on that needs the database lock.** As it stops, the enforcer asks `plan6()` which devices it holds before it hands anything back (`_teardown()`), and while the setting is on `plan6()` takes the database lock for a moment (`steered_now()`). If something is holding that lock just then, as the move of an older household's data to the device tables does (issue 97), the whole hand-back waits for it, over IPv4 as well as IPv6; with the setting off, an enforcer that was between ticks hands the devices back without the lock. `Enforcer.stop()` waits 15 seconds, the program then ends, and what was not put back is put back at the next start, as issue 97 says; a steered device also rights its own IPv6 once the Pi stops answering its checks. This was found by reading the code when the stop-request fix was merged in (25 November) and has not been seen to happen: it needs the setting on while a move is still to do, which means a move that failed and is being tried again. It could be closed by having the last hand-back go by the devices the steerer already holds, without asking for a plan; that is a change to the enforcer and was left for a change of its own.

### 102. The IPv6 DNS announcement trial: what it cannot do, and what is untried

The trial on "Set up a device" (`announcer.py`, off unless switched on) makes the Pi announce itself to every device as an IPv6 DNS server. It was built from the standards and checked byte for byte, but has never run on a real network. What it cannot do, and what is not known:

- **It does not stop a device getting round QuietNet.** The hub goes on announcing its own IPv6 DNS server and can't be told not to. Each device then has two and chooses; Pi-hole users on this hub report that this does not stop the bypass. The dashboard labels are unchanged by the trial, on purpose.
- **It can bring in devices that were never set up to use QuietNet.** The announcement goes to every device on the home network, not only those the owner pointed at the Pi. On a BT hub that is new: until now QuietNet reached only devices set up one by one. A device that takes the announcement up sends lookups to the Pi (Android lists an IPv6 server first), is matched to its card on Devices, and gets the whole-house rules (the advert list, whole-house blocked services and schedules, whole-house "internet off" and the kill switch), its group's rules (the group new devices are put in included, since a device joins that group when a scan first sees it, whether or not it uses QuietNet), and is recorded in the history. A blocked answer is final, so the device does not go on to ask the hub. A parent's phone, a work laptop or a TV that was left out on purpose can so be blocked at a whole-house bedtime. The switch on "Set up a device" and the README say so. Switching the trial off undoes it within seconds. Which devices really take it up is untried (manual step 77).
- **Behind a Wi-Fi range extender, QuietNet can't tell devices apart over IPv6, so the trial holds back while one is known**, and the page says why. An extender shows its devices under its own hardware address. With the device tables in use (the second to fourth parts of the design), an IPv6 address behind one is matched to no device: its lookups are refused while any device is treated differently from the whole house (the device then tries its other DNS server), and otherwise get the whole house's rules alone. Nobody gets another device's rules. On a database not yet moved to the device tables every such address is still judged under one number's rules (issue 96), and one device could be blocked by another's "internet off" or bedtime with a blocked answer, which is final. Left alone, either touches only a device given the Pi's IPv6 address by hand; the trial would make it the ordinary path for every device behind the extender. The hold was written for the older case, and said it could come out once such addresses were treated as unmatched. They now are, but **the hold was left in when the parts were joined**: what a household's devices do when every IPv6 lookup behind an extender is refused has not been tried (manual step 78), and holding back is the choice that changes nothing. Taking it out for a moved database is a decision for the owner. A hardware address seen at two numbers on fewer than three looks does not yet count as an extender, and one behind which only one device uses QuietNet over IPv4 is never seen at two numbers at all. For those, with the device tables, the hardware address's IPv6 addresses are unmatched only while it is live at two numbers at that very look, or while the Pi's IPv6 neighbour table lists it with more than one link-local address (each device has only one). The second sign also holds the trial back, with its own reason on the page, and a goodbye is sent if it appears while announcing. What stays open: **If only one device behind an unrecognised extender has ever spoken to the Pi over IPv6**, there is a single link-local address and it is still taken for the known device, which may be the wrong one: that device's lookups over IPv6 get the known device's rules, blocked answers included, until a second device behind the extender speaks to the Pi over IPv6 or the extender is recognised. Nothing can tell them apart. And Linux keeps stale IPv6 entries, so one device that once had two link-local addresses (or gave itself a second) stays unmatched over IPv6, and holds the trial back, until the old entry goes or the Pi restarts. A device that answers on the network for others under its own hardware address (an Apple TV or HomePod is reported to do this for sleeping Macs) would look the same; whether any does so over IPv6 towards the Pi is not known. On an older database not yet moved, the second sign leaves those addresses unmatched as well (refused while any device is treated differently), and the trial holds back for it; without that sign, a device behind such a hardware address can still get the other's rules on lookups it sends to the Pi over IPv6. Whether a BT disc shows its devices this way over IPv6 is not known (manual step 78).
- **Where a router hands out IPv6 but names no IPv6 DNS server, the trial holds back.** There the Pi's would be an Android phone's only IPv6 DNS server and would complete the phone's IPv6 set-up (an address, a route and a DNS server). Losing it again (a goodbye on switching off, on a clean stop or when QuietNet stops answering for a moment; the 10 minutes running out after a power cut; a sleeping phone missing three announcements) makes Android treat its IPv6 set-up as lost, and it drops off Wi-Fi or switches IPv6 off until it reconnects. So the trial announces only when it has heard a real router within the hour that names an IPv6 DNS server other than the Pi (a BT hub is reported to name itself), or when it has listened for 2,000 seconds (longer than a router may leave between announcements) and no real router has been heard in the last hour (nobody then has an IPv6 route). After a restart it therefore waits, saying so on the page: until the hub's next announcement with the hub's IPv6 on, about 34 minutes with it off. The Android behaviour is from its published source as remembered, not tried on a phone, and not checked against the source for this build. A DNS server handed out only by DHCPv6 is not heard by the Pi, so a router that names its server that way holds the trial back although devices other than Android have a server. If the hub stops naming its server while the trial is announcing, one goodbye is sent, which on such a router is itself the harm; that cannot be avoided once announcing has begun (manual step 79).
- **If the Pi loses power, or QuietNet is killed without warning, there is no goodbye.** Devices keep the Pi's address until its 10 minutes run out, and those that put it first may be slow to look names up, or fail, meanwhile. How slow, on each kind of device, is not measured (manual step 75). A shorter lifetime would make Android ignore the announcement.
- **Whether the hub passes the announcements on is not known.** They go to every device through the hub's Wi-Fi. A hub that filters router announcements from ordinary devices would make the trial do nothing; the dashboard would still say "Announcing now", because the Pi can't tell (manual step 70).
- **Whether devices accept it is not known.** A device written to the older standard may ignore a DNS server from an announcement whose router lifetime is 0. Which devices list the Pi, and whether before or after the hub, needs checking on each kind (manual step 71).
- **It names the Pi's link-local address (`fe80::…`),** not the address "Set up a device" gives for typing in. That address is always there, and a BT hub names its own link-local address the same way, but a device that mishandles a link-local DNS server would ignore the Pi or fail to reach it. The Pi answers each lookup from the address it was sent to (issue 101's reply path, live for every home on Linux). With two link-local addresses on the card that is untried: if the system refused to send from the asked address, the answer would leave from the address the system picks, a device would throw it away, and the Pi's own test question could not notice. So the trial still holds back, with the reason on the page, while the card has more than one, until manual step 80 has been run; if each answer there comes back from the address asked, taking the hold out is the owner's decision.
- **The Pi's message has both DHCPv6 flags clear, and for those flags clear is not "nothing to say".** A router announcement carries two flags, "get your addresses from a DHCPv6 server" (M) and "get other settings from one" (O). In the Pi's message both are clear, as the design requires, which reads "DHCPv6 is not used here"; a router that sets either says the opposite, and the standard expects every announcer on a network to agree. Windows is reported (not tried here; from published reports as remembered) to keep one setting per network connection, whichever announcer spoke last, and to give up what it got from DHCPv6 when a flag goes from set to clear. So the trial holds back, with the reason on the page, while a real router heard in the last hour sets M: a Windows computer could otherwise lose and regain its IPv6 address every few minutes. With O alone it still announces, and a Windows computer may drop and fetch again its DHCPv6 DNS servers every few minutes, keeping the servers named in announcements meanwhile (a BT Smart Hub is reported to set O). The hub's own flags are shown under `ipv6.routers` in the status (`managed`, `other`); record them here once seen (manual step 82). Sending the same M and O as the real router, which is what the standard expects of a second announcer and what Thread border routers are reported to do, would remove the disagreement, but needs the owner's say: the design and the guide for editors forbid DHCPv6 flags in this message.
- **A lookup from a device's link-local address must still be matched to the device.** Until it is (its first seconds), and while any device is treated differently from the whole house, it is refused, as any unmatched IPv6 lookup is (issue 5), and the device tries its other server.
- **The "is QuietNet answering?" check is made from the Pi itself,** to its own address. It proves the filter is listening and answering there, not that every device can reach it: a firewall on the Pi that lets the Pi's own traffic through but drops the home network's would not be noticed.
- **A device that has just joined waits for the next announcement,** up to 200 seconds, because the Pi does not answer devices asking for a router. Until then it has only the hub's server.
- **With the hub's IPv6 switched off the trial still announces** (once it has listened for 2,000 seconds and heard no router). The Pi is then the only IPv6 DNS server any device is told of, so everything above about devices that were never set up goes for every device that takes DNS from announcements, not just for some. After a power cut all of them, not only the devices the owner set up, may be slow to look names up for up to 10 minutes. What devices do with an IPv6 DNS server and no IPv6 internet address is not tried (manual steps 71 and 77).
- **A goodbye the Pi cannot send is tried again, but may never arrive.** If the card refuses the frame, or is gone, when devices should be told to stop, the Pi tries again every 20 seconds for as long as devices still hold the address (10 minutes from the last announcement), from the card's present address or, failing that, the one it last announced from. On a clean stop there is one go only, because the program is ending; the log then says the message could not be sent. Devices that never hear it drop the address when its 10 minutes run out. Whether a frame still leaves a card whose IPv6 has been switched off is not tried (manual step 81).
- **A clean stop's two waits add up to all the time Docker allows.** The clean-up waits up to 15 seconds for the enforcer and then up to 5 for the announcer's goodbyes, and the container is given 20 seconds to stop (`stop_grace_period`). The two overlap (the goodbyes go out while the enforcer hands the network back, and need about four seconds at the outside), so the sum is reached only if both threads are stuck at once; then Docker's kill comes as the second wait ends and the closing line may be lost. No timing was changed for this when the stop-request fix was merged in; whether to lengthen the container's stop time or shorten a wait is the owner's choice. Not timed on a Pi (manual steps 17 and 74).
- **A second announcer on the same Pi** (the system's own `radvd`, say) naming the same address would have its announcements called off whenever the trial sends a goodbye.
- **On a Mac, or without the right to send raw frames, it does nothing** and the page says so.

### 18. The local dashboard has no password

Anyone who can open `http://localhost:8377` on the QuietNet computer controls it: another account on the same machine, or anyone with an SSH login. This is by design for a single-owner home machine. It matters if the Pi is shared.

## Open: smaller security points

### 7. Relay

Four of the six points were fixed on 23 November (see below). Still open:

- The overall cap on wrong pairing codes was raised from 20 to 200 in 10 minutes, now that each network address has its own cap of 20. Codes are 32 bits, so someone guessing without stop has about a 1 in 400 chance a year of hitting a given live code, against about 1 in 4,000 before. Judged acceptable; the owner may want to confirm.
- The relay's room for large answers (48 MB) counts each answer's stated size. While one is being read, memory briefly reaches two to three times that size.
- The guard against login forgery relies on the browser's `Sec-Fetch-Site` header. Browsers that don't send it (for example Safari before 16.4) are still exposed. Closing that fully would need a one-time form token tied to a cookie set before sign-in. Low risk: the visitor would see the attacker's QuietNets, not their own.

### 21. The Pi container runs as the root user

Since 23 November the relay gives up root at start-up (see below). The Pi container still runs as root: it needs network rights (raw sockets, the firewall, kernel settings) that are simplest to hold as root.

## Open: minor

### 12. Minor

- The enforcer drops addresses handed out in the last six hours. A service that moves to new addresses is covered as soon as the device looks them up through QuietNet.
- An address a blocked service shares with an allowed site is spared only once QuietNet has handed that address out for the allowed site in the last six hours. Until then it is dropped, so the first connection to a rarely used allowed site on the same front door can stall for up to two seconds (the next plan) before it is spared. And while an address is spared, a connection to the blocked service that was already open on it is not cut; new ones still fail at the name.
- The look (theme) cookie `qn_theme` on the Pi's own dashboard (`localhost:8377`) is shared with every other page served from `localhost`, whatever the port, because browsers do not keep cookies apart by port. Harmless: it is only a display choice, checked against the three names wherever it is read.
- Like the relay's other forms, the Appearance form (`POST /theme`) relies on `Sec-Fetch-Site` against other websites; a browser that does not send it could be made to change its own look. Harmless: it changes only how the pages look, in that browser.
- A request to stop that arrives before the program has begun to listen for it is not handled. Since 25 November the program listens from the first lines of `server.py`, before it loads the parts of Python it uses (see "Fixed"), so what is left is the time Python itself takes to start and to read `server.py`: about 25 thousandths of a second on a Mac, 30 to 45 in a test container given one processor, and 60 to 80 in one held to half a processor (all measured); perhaps a few tenths of a second on a Pi (not measured). Nothing has been started by then, so nothing needs cleaning up; what happens to the request depends on where QuietNet runs. Started by hand, the program simply ends there (Ctrl-C shows a short Python traceback). **In its container it is the container's first process, and Linux does not pass a signal to a container's first process until that process has asked for it, so a `docker stop` in that first moment is dropped**: QuietNet starts up and runs as if nothing had been asked, Docker waits out its 20 seconds and kills it, and the clean-up does not run, as after a crash (what the enforcer changed is put back at the next start). This was shown on 25 November with the program as the first process of a test container: held to half a processor, a request 60 thousandths of a second after launch was dropped and one at 100 was acted on; given two processors, one at 20 was dropped and one at 40 was acted on. No line of `server.py` can run before Python has read the file, so the moment cannot be closed altogether from inside it. One line in `docker-compose.yml` would close it, `init: true`, which puts Docker's own small first process in front of QuietNet so that an early request ends Python at once, before anything is started; that is a change to the container and needs trying on a real Pi, so it is left for the owner to decide.
- Ctrl-C in the first hundredth of a second after QuietNet is started can be swallowed by Python itself. While Python is still working out where to load the program from, before the first line of `server.py`, it meets the interruption inside its own start-up, prints "Failed checking if argv[0] is an import path entry" with a short traceback, and carries on: QuietNet then starts and runs as if nothing had been pressed, and Ctrl-C has to be pressed again. Seen on 25 November in 8 of 180 Ctrl-Cs sent in the first 14 thousandths of a second in a test container (at 5, 6 and 10 thousandths; Python 3.13), and in 2 of 1,103 sent on a Mac at up to 300 (at 7 and 11 thousandths; Python 3.9 and 3.14). Only Ctrl-C does this, not `docker stop`'s signal, and nothing has been started by then. It is Python's own doing, and no line of `server.py` can prevent it.
- A request to stop that arrives while the cloud link is making its first pairing try (only on a start with `QUIETNET_PAIR` set and no pairing yet) waits for that try to finish before the clean-up starts. The try normally takes well under a second, but can take 20 if the relay cannot be reached, which is as long as Docker waits before it kills the program; the enforcer has been started by then. A request before or after the try is acted on at once.
- Closing the terminal window that QuietNet runs in ends it at once, with no clean-up: the signal a closing terminal sends (SIGHUP) is not listened for, only `docker stop`'s and Ctrl-C's. On a Mac, where the start-up lines say to close the window to stop QuietNet, the enforcer never runs and nothing is left behind. On Linux, a QuietNet started by hand with admin rights from a terminal or a remote session that is then closed leaves its steered devices as they were until the next start, as after a crash.
- The dashboard prints a Python traceback ("Exception occurred during processing of request", ending "BrokenPipeError" or "ConnectionResetError") whenever a browser's connection is reset before its answer has been written. Harmless: only that one request is affected. It was seen while measuring the stop-request fix on a Mac, which resets connections when more than five arrive at the dashboard at once; it has nothing to do with stopping, and happens with or without a request to stop.

### 95. Names a device's own system needs: what is left

Issue 95 (below, under Fixed) added a short table of names a device's own system needs (`NEEDED` in `server.py`), a question before blocking one, and a note beside a block that already exists. What that leaves open:

- **The table is a short, hand-kept list**, not a full one. A device not on it (a Sony or Philips TV, a smart speaker other than Echo, a printer) can still have a needed address labelled "Possibly junk". The general "this doesn't look like an advert or tracker" question is still asked for names with no label, but not for "Possibly junk" ones. Names considered and left out for want of certainty: `samsungotn.net` (Samsung TV updates), `lgtvcommon.com` (LG), `amazon.co.uk` and `amazonalexa.com` (Echo), `nintendowifi.net`, `xbox.com`. Two were added after a second look: `samsungqbe.com` (four owners separately report a Samsung TV's online check, first set-up, an update or its app shop failing until it was allowed) and `lge.com` (LG TVs' system updates and the Content Store's downloads sit under it, and blocking the whole name is reported to stop every LG service on the TV). The evidence for both is owners' reports, not the makers' own documents, and one guide calls `samsungqbe.com` an advert name without saying what breaks.
- **Only the whole name asks.** Blocking a sub-name that a device needs (`time.samsungcloudsolution.com`, say) does not ask, by design: sub-names are how a single tracker is blocked, or how LG's updates are held back (`snu.lge.com`).
- **Blocking a whole service does not ask.** The PlayStation, Xbox and Nintendo switches under "Block apps and services" cover names in the table, and are a deliberate choice with their own switch.
- **A needed name on an advert list is still blocked automatically, with no note.** A whole needed name on the downloaded list would be blocked (`why` is `list`); the row then shows "Advert / tracker" and "Needed by ..." together, but no note, because the note is only for a block the person made. None is on the built-in list (a test checks).
- **The community list blocks sub-names that Samsung TVs are reported to need, and the page gives no hint.** The optional community list (StevenBlack), as read on 24 November, holds `lcprd1.samsungcloudsolution.net`, `lcprd2.samsungcloudsolution.net` and `oempprd.samsungcloudsolution.net` (and `vdterms.samsungcloudsolution.com`). Where the owner has downloaded that list, these stay "Blocked automatically" beneath a group that reads "Needed by Samsung TVs" and "Partly blocked", with no note. Some owners report that a Samsung TV's apps may not open without `lcprd1.samsungcloudsolution.net`; others found that allowing it alone was not the whole cure. So in such a household the trouble that started issue 95 may still happen with nothing on the page pointing at the cause. Unblocking the whole name does not allow these sub-names. The remedy is to open the group on the TV's page and press Unblock on that sub-name, which keeps it allowed from then on. Whether QuietNet should spare such sub-names, or say so on the page, is a decision for the owner; no test reads the real list.
- **Away from home, the question appears only once the relay has been redeployed.** The relay serves its own copy of the page, built into its image. With the Pi updated and the relay not, the page away from home shows no "Needed by" labels and cannot ask, so the Pi refuses a whole needed name there; the old page shows the refusal sentence, which says to block the name from QuietNet's own page at home. The other way round (the relay updated, the Pi not) nothing is labelled or asked and blocks go through as before.
- **Enter still answers yes to every other question.** Only the needed-name question puts the keyboard on Cancel. The others (the kill switch, deleting a schedule or group, forgetting a device's history) keep the yes button under Enter, as before; a held-down Enter no longer answers any of them, but a second press does.
- **Not yet tried on a real TV or through the relay in a browser.** What has and has not been run is under 79.

### 90. The three looks: what differs from the mockups, and what is untried

Added on 23 November (Calm, Household and Control room, on the dashboard and the relay). Not faults, but gaps to know about:

- **System fonts, not the mockups' fonts.** The mockups use Inter, Space Grotesk and JetBrains Mono, loaded from Google Fonts. QuietNet loads nothing from other websites and ships no font files, so the pages use fonts already on the device: the system's own sans-serif (San Francisco, Segoe UI or Roboto) for text, a rounded system face for Household's headings where there is one (Apple devices; elsewhere the plain sans-serif), and the system's monospace face for addresses. The pages therefore look close to the mockups but not identical, and differ a little from one platform to another.
- **The choice belongs to the browser, not the account.** It is a cookie (`qn_theme`), so each browser and device remembers its own, and signing in elsewhere does not bring it along. The Pi's own dashboard (`localhost:8377`) and the relay are different websites, so a look chosen on one is not carried to the other; the relay and the dashboard opened through it do share one.
- **The relay's sign-in pages cannot change the look.** Choosing one needs a signed-in person (`POST /theme`); signed out, the pages use whatever the cookie already says, else Calm.
- **Control room has no light version.** It is always dark, whatever the device is set to.
- **With scripts switched off the dashboard shows Calm** for every choice, because its look is picked by a small script. The dashboard needs scripts to work at all, so this matters little. The relay's pages are drawn in the chosen look on the server and need no script.
- **The kill switch has no "arm, then switch" step** as in the Control room group mockup: it keeps the confirmation dialog every look has, so it behaves the same in all three.
- **Not yet tried in a real browser on every platform.** The tests check the page's text (the early script, each look's colours, no outside requests, no inline styles), not how it is drawn. Older Safari (12 to 14.0), Firefox on Android and Windows high-contrast mode in particular are untried; see [Testing](TESTING.md) for the manual checks.

- Fixes to `tarfile`, `zipfile`, `tempfile`, the XML parser and `mimetypes`: QuietNet does not use these.

On a Mac, running QuietNet with a current Python from python.org is safer than Apple's 3.9, though the scan feature works best with Apple's (see the launcher's comment).

### A request to stop that was lost, or that skipped the clean-up (25 November)

A request to stop is the signal that `docker stop` and a system shutdown send, or Ctrl-C. `main()` in `server.py` turned it into an interruption (Python's `KeyboardInterrupt`) raised at whatever line the main thread had reached, and caught it only round the dashboard's serving loop. That went wrong at two moments, both found through the shutdown tests and listed until now under 12. When the clean-up does not run, the enforcer does not hand devices back to the router, and they are left pointing at a program that is gone until the next start.

The other two, `test_the_running_loop_starts_the_listener_with_the_stop_signal` and `test_a_fault_in_ipv6_steering_does_not_stop_the_ipv4_tick` in `tests/test_enforcer_ipv6.py`, start the enforcer's own thread and wait for it to start the listener or to run a tick. They looked again for two seconds and then gave up, so a thread held up for longer than that failed them (shown by holding it up for four seconds). They now look for up to ten seconds, and still stop waiting the moment the thread has done it.

Nine more were found among the tests that came with the IPv6 DNS announcement trial, all in `tests/test_announcer.py`, and none had failed on GitHub. Eight are tests of the test question (`TheTestQuestion`). They ask a stand-in DNS server that answers from a thread of its own, and that notes each question only when that thread gets round to it. `test_quietnet_answering_counts_as_answering`, its twin over IPv6, `test_the_question_is_a_bare_twelve_byte_header_with_no_name_in_it` and `test_an_answer_to_the_second_question_is_enough` gave the stand-in 0.1 or 0.2 seconds to answer, so a thread held up for longer failed them (shown by holding it up). The first three now allow five seconds, which costs nothing because the asker returns as soon as an answer is in; the fourth, whose first question has to go unanswered for the whole wait, allows one second. `test_the_question_is_asked_again_once_before_giving_up` counted the questions the stand-in had noted the instant the asker gave up, 0.05 seconds after the second was sent and with nothing waiting for the stand-in's thread, which is the relay test's fault again. With the whole test process frozen from outside for 0.06 seconds at a time it failed 4 times in 600 with Python 3.14 and 29 times in 600 with Apple's Python; it now waits up to five seconds for the questions to be noted (`questions_reach()`), and under the same freezing did not fail in 1,200 and 600 goes. The three tests of an answer that must not count (a wrong number, the question sent straight back, a cut-short answer) gave the stand-in 0.05 seconds: a slow thread could not fail them, but it made them pass as silence, with the answer never looked at. They now allow five seconds, which is not waited out because an answer that does not count ends that go at once, and check that both questions were had. The ninth, `test_the_status_says_what_is_being_announced`, checked that the time the status gives for the last announcement was within five seconds of the present; it now reads the clock just before and just after the announcement is sent, and the time must lie between the two. The tests that start the announcer's own thread already wait for it in the right way (look again for up to five seconds, then check), and the rest drive it one step at a time with a stand-in clock.

The whole suite was then run with this computer's clock set, before every test, to 23:59:20, to 00:00:05 and to 12:59:58, each on a weekday, a Saturday and a Sunday, and passed each time. `docs/TESTING.md` has a note for anyone writing a test that needs "now".
