# Changelog

## Unreleased

Device table, address record and history (second part of the IPv6, DNS and device identity design; 24 November):
- **New: one device is one hardware address.** New tables `device` (kinds: by hardware address, by network address only, this computer, the home router; numbers are never used twice), `device_hw` and `address_use` (a dated record of which device used which address). Each lookup in the history carries the device it belonged to when it was made. A TV that moved from `.65` to `.67` is one device with one history; a phone's many IPv6 addresses come to one device; and an address handed from one device to another no longer hands over the history.
- **New: a map of which device has which address now** (`S.addr_device`), kept by looking at the neighbour tables every 5 seconds, never on a lookup. A lookup finds its device with one dictionary lookup and no database call. Safeguards: only an address confirmed just now counts (a stale entry may belong to a device that has left); an address that turns up with another hardware address changes hands at once; one hardware address at two live addresses keeps only the address it already had; a range extender's addresses are each a device of their own; a new private hardware address is a new device, never merged automatically; an address built from a hardware address proves nothing.
- **New: this computer and the home router are fixed devices** (`pi`, `hub`), never mixed with others.
- **New: a clean-up pass each minute** files the lookups that were saved without a device (their address was not confirmed at that moment) against the device the address record shows was there, in small steps that let go of the database between them. A lookup nobody can be matched to after 3 minutes is filed under its address.
- **New: `GET /api/devices` lists one entry per device**, with `id`, `kind`, `macs` and `addresses`. `ip` is the address the entry is shown and controlled under; a device that has left and whose address went to another has none, and is listed only with `?all=1`, so an older page is never handed a card it cannot open. `GET /api/activity` takes `device=<number>` for a device's whole history and still accepts `ip=`; `POST /api/clear-history` takes `device` and clears only that device's history. `GET /api/status` has a new `devices` part. The dashboard page passes the number where it has one; it still shows cards by address.
- **New: an older household's database is moved over after start-up**, once the filter is answering and the enforcer has started, never before. It needs free space of twice the database's size (otherwise it waits, says so on the home page and tries again each hour), keeps a copy of the database as `quietnet.db.before-devices`, and does everything else in one transaction: any error rolls it back, and QuietNet carries on with the old tables exactly as before and says so. Older history is then given its device in the background, 2,000 rows at a time, newest first, and carries on after a restart. How to go back is in `docs/ARCHITECTURE.md`.
- Rules, names and groups are untouched and still kept under addresses: holding them against the device is the next part.
- History questions still use an index: a new index by device then time (`q_device_ts`), and tests of every new query plan. A test moves and fills a two-million-row history.
- Docs: `docs/ARCHITECTURE.md` has a new part, "One device, many addresses"; `docs/API.md` describes the new fields and parameters; `docs/KNOWN_ISSUES.md` has what was fixed and the new open issue 97; `docs/TESTING.md` has manual steps 28 to 35 for a real Pi.
- Fixed in the check of this build, before release (the table is in `docs/KNOWN_ISSUES.md`):
  - **A name or rule set on the card of a device that was away vanished from the device list when the device came back at another address,** still in force and waiting for the next device given that address. `GET /api/devices` now lists every address that carries a name, a group or rules, whoever has it now and whether or not it has history or a recorded owner. An address whose name was cleared is not listed for that alone.
  - **`GET /api/devices` could list one address twice** when an old scan had seen another device there and the address carried a name, rules or a warning. What an address carries now shows only on the entry of the device listed under it.
  - **The copy kept before the move (`quietnet.db.before-devices`) held the household's history for good.** It is now deleted 30 days after the move, and at once when everyone's history is forgotten. Forgetting one device's history leaves that device's older lookups in the copy until then; the README says so. Going back by the copy is possible only while it is there.
  - **The move could run before the Pi knew its own address** (a start before the Wi-Fi is connected), filing this computer's and the router's older history under devices that are not shown. It now waits up to two minutes for the address and looks for the router afresh first.
  - **Lookups made in the second before the move could be left without a device for good in a small household.** The fill of older history no longer calls itself finished until 10 seconds after the move, when the history writer has caught up.
  - **The IPv6 look no longer waits for the database,** so lookups from a new IPv6 address are still matched to their device, not refused, while an older household's data is being moved.
  - **`POST /api/clear-history` with a device number too large to be a number dropped the connection.** It now answers as for any unknown device number.
  - Left open and now written down (issue 97): no warning yet when an older version has been run on a moved database, and what happens to the lookups it recorded.
  - New tests: that start-up starts the device keeper only after the filter and the enforcer and never runs the move itself; one round of the real history writer; clearing by device number alone; a device seen again being kept; and one for each smaller documented behaviour that had none. `docs/TESTING.md` says what `test_shutdown.py` reads from the real computer.
- Joined with "Names a device's own system needs" (below): the activity list asked for by device number (`GET /api/activity?device=`) carries `needed` like the list by address, so the page shows "Needed by ...", asks before blocking and shows the note on a device's card whichever way it asked. A new test covers a needed name looked up at the address a device had before it moved. To make room for that change's issue 95 and manual check 16, the device tables' open issue is now 97 (it was 96 while this was being built) and its manual steps are 28 to 35 (they were 27 to 34).

IPv6 honesty and small fixes (first part of the IPv6, DNS and device identity design; 24 November):
- **New: "Set up a device" says how to switch IPv6 off on a BT Smart Hub**, the only fix that covers every device: Advanced Settings, IPv6, Configuration, Allocation Mode "Off"; or "ULA Enabled" where there is no off switch. Each comes with what to do afterwards (reconnect devices, check consoles and work laptops) and how to undo it.
- **New: an "IPv6 is off on your hub" confirmation**, shown only on evidence: QuietNet has listened for the router's announcements for a full hour without a break while able to hear them, heard no real router, holds no public IPv6 address itself, and nothing in the home names an IPv6 DNS server other than QuietNet. A restart starts the hour again, a listener that never started says "can't tell", and the hour is measured by a steady timer so a Pi learning the time can't shorten it. New `hub_off`, `listening_for`, `can_hear`, `routers`, `neighbours_ok` and `taking_lookups` in the `ipv6` part of `GET /api/status`.
- **New: honest labels.** While the home network has IPv6, or anything in it names an IPv6 DNS server that is not QuietNet, every device that uses QuietNet is marked "Can bypass over IPv6" (new `v6_bypass` in `GET /api/devices`), steered or not, and its page says why and what fixes it. The "Cut live connections" card now says it covers IPv4 only, in place of saying the device "uses IPv4 instead".
- **New: an optional switch, "Give no device IPv6 addresses"**, off unless turned on (`POST /api/no-ipv6-switch`, `no_ipv6_all` in the status). On, every device gets "no records" for IPv6 address, HTTPS and SVCB lookups, as devices with "Cut live connections" already do. Never for names only the home network can answer, nor for QuietNet's own machine. It takes effect, and is undone, on the next lookup.
- **Fixed: an IPv6 lookup QuietNet couldn't match was answered in full while a device had only "Cut live connections" on or was in a group with no rules.** That handed back IPv6 addresses the cut is meant to withhold, and escaped the block on other DNS services. Such lookups are now refused, as they already were when a device or group rule existed.
- **Fixed: a new IPv6 address was unmatched for up to a minute.** A lookup from one now sets off a look at the neighbours at once (at most every 2 seconds) and waits up to 0.4 seconds for it. The look runs on the watcher's thread, never inside `decision()`.
- **Fixed: a stale neighbour entry could beat a reachable one,** filing a device's IPv6 lookups under a number it no longer has. Reachable wins, then unknown, then stale; failed and unfinished IPv6 entries are dropped.
- **Fixed: a device's share of the DNS listeners was counted per address and per listener.** It is now one per device across IPv4, IPv6 and all its matched addresses. An IPv6 address behind a Wi-Fi range extender keeps a share of its own, since an extender's hardware address stands for several devices.
- **Fixed: if the IPv4 port couldn't be opened, IPv6 was never tried.** Each is now tried whatever happened to the other.
- **Fixed: the hub's IPv6 address was thrown away.** The announcement listener keeps a real router's link-local address and reads its hardware address from the announcement. Nothing acts on them yet.
- **Fixed: "Set up a device" said a device's name, group and blocks won't follow it to a new number.** They do.
- An IPv6 address built from a hardware address is only ever a hint: an unmatched card says "Probably the same device as ..." (new `same_as` in `GET /api/devices`), and no rule is applied from it.
- The home page says when the list of IPv6 neighbours can't be read, in place of IPv6 lookups being refused with nothing said.
- Docs: `docs/ARCHITECTURE.md` has new parts on matching IPv6 addresses to devices, the confirmation and the switch; `docs/KNOWN_ISSUES.md` has the fixed faults and the new open issue 96; `docs/TESTING.md` has manual steps 17 to 27 for a real Pi and hub.
- Fixed in the check of this build, before release (the table is in `docs/KNOWN_ISSUES.md`):
  - **"IPv6 is off on your hub" could be shown while a router still named its own IPv6 DNS server.** A router with no IPv6 internet but a private range announces with a router lifetime of 0 and can still name itself; devices use that server. The confirmation now waits until no IPv6 DNS server but QuietNet is named, devices keep the "Can bypass over IPv6" label meanwhile, and "Set up a device" says what is happening.
  - **"IPv6 is off on your hub" could be shown on a Pi whose own IPv6 was switched off**, which hears nothing whatever the hub does. The hour now counts only while the Pi's home network card has a working link-local IPv6 address (`ipv6_on_card()`, new `can_hear` in the status); without one the page says QuietNet can't tell, and why.
  - **Devices behind a range extender shared one device's share of lookups over IPv6**, so one busy device could have the others' lookups dropped. Each such IPv6 address now counts by itself (`S.v6_shared`).
  - Tests added for behaviours that had none: the router card and the same-device hint actually being put on the page; the watcher taking up the "look now" flag; a look saying it is under way; the steady timer being set by a real announcement; a hardware-address option of another size, and the first one counting. `docs/TESTING.md` step 17 no longer expects "Still checking" where the page says "IPv6 is on in your home", and the run time and two descriptions of the live-cut card were corrected.
  - **Four tests of a device's share of lookups failed on Linux only**, which the pull request's automatic Linux run found. On Linux the IPv4 listener asks which address each lookup was sent to and reads with `recvmsg`; the tests' stand-in socket hands lookups over through `recvfrom` only. The tests' helper now switches that option off, since shares are counted the same on every system. A fault in the tests, not in the filter.

Names a device's own system needs (24 November). Found in a real household: a Samsung TV stopped opening apps after `samsungcloudsolution.net`, labelled "Possibly junk", was blocked from its page. Known issue 95:
- **Fixed: an address a TV depends on was called "Possibly junk".** A short table, `NEEDED` in `server.py`, lists about 30 whole names that common household devices need for their own sign-in, app shop, online check, clock or updates. Such a row shows "Needed by Samsung TVs" in place of "Possibly junk"; a name on the advert list keeps "Advert / tracker"; sub-names keep their own labels. New `needed` in `GET /api/activity` and `GET /api/rules`. `samsungcloudsolution.net` is now labelled "Samsung TV".
- **New: blocking such a name asks first.** `POST /api/block` answers `409` with who needs the name unless the request carries `"sure": true`; the dashboard asks ("Samsung TVs need this address for their own system to work. Blocking it may stop them opening apps, signing in or updating. Block it anyway?") and blocks only on a yes. This covers the Block button, a name typed on the Blocked list page, and the dashboard through the relay. Blocking a single sub-name does not ask. What is blocked once a block exists is unchanged.
- **New: a note beside a block that already exists.** On the Blocked list page and on a "Blocked by you" row, a needed name says who needs it and to unblock it if apps have stopped opening.
- **Redeploy the relay with this change.** The relay serves its own copy of the dashboard page, so the labels and the question appear away from home only once the relay has been redeployed. Until then a Pi with this change refuses a whole needed name remotely, and the refusal says to block it from QuietNet's own page at home.
- From the check of this change: `samsungqbe.com` (a Samsung TV's online check, set-up and app shop; now also labelled "Samsung TV") and `lge.com` (LG TV updates and Content Store downloads) are in the table. A needed name's row no longer reads "Advert / tracker" because the only names seen beneath it were advert sub-names (`logs.roku.com` under `roku.com`); it does only when the whole name is on the advert list. In the question, Cancel holds the keyboard and Enter presses only the button it is on, and a held-down Enter answers no question and sends a typed name once, so typing a name and pressing Enter twice no longer blocks it. The refusal sentence no longer promises that a reload is enough. `tests/test_packaging.py` names a throwaway data folder before importing `server`, so running its classes by name ahead of others can no longer clear the checkout's own `data` folder. What is left is in known issues 95 and 79.

Tests that failed by the clock or by timing (25 November). Tests and docs only; nothing QuietNet does has changed. See `docs/KNOWN_ISSUES.md`, "Tests that failed by the clock or by timing":
- **Fixed: six tests failed when run during the minute 23:59.** They made a schedule from 00:00 to 23:59 and took it to be in force now; a schedule's end is not inside it. New shared helper `in_force_now()` in `tests/test_quietnet.py` (and its opposite, `not_in_force_now()`) gives a window worked out from the clock, and every test that means "in force now" uses it. Three more tests used the same schedule and passed at 23:59 for the wrong reason (what they checked is just as true with no schedule in force); two of them now check first that the schedule is biting.
- **Fixed: the shutdown tests could ask the program to stop before it was ready.** They now wait until the dashboard has answered a request, not merely until its port takes a connection, and then pause half a second before asking. The two faults in the program that this showed are not fixed and are listed under known issue 12: a stop request in the last moments of start-up ends the program without its clean-up, and one that arrives in the instant the dashboard takes a new connection can be lost altogether (the reason for the pause).
- **Fixed: a shutdown test that failed because the program died or hung did not say why.** Every such failure now shows what the program printed; a program that died after opening its port is reported as "stopped during start-up" and no longer as "did not answer within 30 seconds".
- **Fixed: a relay test checked too soon that the room for a large answer had been given back.** The relay gives it back just after writing the answer. The test now waits up to five seconds for it, as do two tests of the relay's connection limit that relied on a short sleep.
- **Fixed: a test run on Python 3.13 or later printed hundreds of `ResourceWarning: unclosed database` lines**, each quoting whatever line of code was running at the time. That is where the lines `raise AttributeError(name)` in GitHub's Linux logs came from: they were never errors. The tests open the database afresh before every test and left each old connection unclosed. `tests/test_quietnet.py` now closes the connection that `server.init_db()` replaces, for every test file, and two relay tests close theirs. At most one such line is still printed, as Python exits.
- **Fixed: a relay test that passed could print a Python traceback from its pretend Pi**, when the relay closed the connection on a large answer it had no room for while the pretend Pi was still sending it. The pretend Pi now takes that as nothing wrong.
- Docs: `docs/TESTING.md` and `AGENTS.md` say that a test must not depend on the time of day or on a sleep being long enough, and name the helper.

Licences on the relay, first phase (relay only; nothing changes on the Pi):
- **New: one licence per account**, in new `licences` and `licence_log` tables. `licence_state()` works out the state (none, trial, active, cancelling, past due with 14 days' grace, expired, revoked; active counts as expired 3 days after its end date) and what it allows: remote access, updates, adding and pairing Pis.
- **New: `QUIETNET_LICENCE_GATE`, off by default.** While off, nothing is refused; what would have been refused is logged (a log line and a `licence_log` row, at most once an hour per account and kind of refusal). With it on: the Pi's page becomes a "Remote access is paused" page and dashboard calls get `402`; adding a Pi needs a licence that allows it and a free seat; `POST /agent/pair` answers `403` with the reason and the licence state. Never `401` for a licence reason.
- **New: every account that exists when licences arrive gets a `legacy` licence**, active for 90 days, with seats for its Pis (at least 2), once only.
- **New: the paused page keeps two rescue buttons** (`POST /pi/<id>/rescue`): "Turn the internet back on for every device" and "Pause blocking for an hour", in every licence state and with the gate on or off. The relay sends only fixed calls (`/api/rescue` for a 0.6 Pi, `/api/kill {"on": false}` for an older one, `/api/pause {"minutes": 60}`), and logs each.
- **New: seats and install ids.** A licence covers 2 Pis unless the owner changes it. A Pi may send its install id when pairing; pairing again with the same id replaces its old, offline entry, and is refused while that entry is online (a copied SD card).
- **New: poll answers carry a `licence` object** (and `latest` when `QUIETNET_LATEST` is set). Polling is otherwise unchanged; older Pis ignore the extra keys. The Pi's `X-QuietNet-Agent` header is recorded.
- **New: a Licence card on the home page** with one sentence per state and "Pis: N of M"; paused Pis say "Remote access paused".
- **New: the owner's command line**, `python relay.py licence show|list|grant|revoke|restore|seats`, which gives up root before opening the database. Documented in `cloud/README.md` with the go-live steps; manual checks in `docs/TESTING.md`; gaps in known issue 94.

- Rules move onto an address left with only a name or a departed visitor's group; a moved device no longer inherits the visitors' group.
- A device that changes its private Wi-Fi address but gets the same number back keeps its rules, and the owner is asked "Is it the same device?" (new `POST /api/different-device`; `POST /api/move-rules` with one address twice means "yes"). A paused device's page offers "It's the same device".
- A device never seen before at a paused address gets the new-device group.
- The neighbour table is read with `ip -4 neigh`, so a stale entry at a device's old address no longer holds its rules back.
- A Wi-Fi range extender showing every device behind it with its own hardware address is recognised, and rules no longer jump between the devices behind it.
- The record of hardware addresses is capped (30 days, 5,000 addresses) and only the ones on the network now are looked up.
- Other DNS services are blocked only for devices the owner controls, unless the new home-page switch "Stop every device using another DNS service" is on (`POST /api/other-dns-switch`, `other_dns_all` in the status), so phones set to use one strictly keep working.
- YouTube's, Netflix's and Twitch's video servers are always cut by address, even when an allowed download name shares them.
- Router announcements must arrive with a hop limit of 255; only those from a real router (lifetime above 0) count as the network having IPv6, or decide which unique-local address devices are given.
- Dashboard page tests for the device-move notices, recent device changes, the new-device group picker, the badges, the device warning and the other-DNS notice and switch. A wrong "below" in KNOWN_ISSUES corrected.

Rules follow the device (23 November):
- **Fixed: rules belonged to the IP address,** so a phone with a new private Wi-Fi address or a new number lost every rule, and a device later given the old number took them on. Each address's rules are now tied to the hardware address seen there: when the device moves to a free address they move with it (with a note on the home page); when a different device takes the address they are paused until the device comes back; and when the new address has rules of its own, both devices show a warning instead of merging. New `paused` and `warning` in `GET /api/devices`.
- **New: "New devices go into group"** on the Groups page puts a device never seen before into a chosen group (none by default). New `POST /api/new-device-group` and `new_device_group` in `GET /api/status`.

Shared addresses and "Cut live connections" (23 November):
- **Fixed: blocking YouTube on a device with "Cut live connections" on also cut Google search, Classroom, Docs and Gmail.** They share Google's front-door addresses, and the same could happen with sites on Cloudflare, Fastly or Akamai. An address is no longer dropped for a device if a site that device is allowed was given the same address in the last six hours. The blocked service is still blocked by name, and addresses only it uses (YouTube's video servers) are still dropped; bedtime, the kill switch and the internet switch still cut everything. The device's "Cut live connections" card says when some addresses were left to the name block; new `shared` in `GET /api/enforcer` and in `enforcer` in `GET /api/status`.

Other DNS services (23 November):
- **Fixed: a device could get round every name block by using another DNS server.** The well-known encrypted DNS services (Google's `dns.google`, Cloudflare's `cloudflare-dns.com`, Quad9, OpenDNS, NextDNS, CleanBrowsing, AdGuard, Mullvad, DNS.SB and Control D, with every name beneath them) now get the blocked answer for every device, paused or not, so Android's Private DNS or a browser's secure DNS set to one of them falls back to ordinary DNS. The list is `OTHER_DNS_SERVICES` in `server.py`. The device page and the device list say "tried to use another DNS service"; new `other_dns` in `GET /api/devices` and `/api/activity`.
- **New: for devices with "Cut live connections" on, ordinary DNS sent to any other server (8.8.8.8, the router) is answered by QuietNet,** and Private DNS and DNS over QUIC (port 853) are dropped. Only the `nft` tool does the redirect; `GET /api/enforcer` has a new `dns_redirect` to say whether it is on. On Linux, answers now leave from the address each lookup was sent to, which the redirect needs.

The router's own IPv6 DNS server (23 November):
- **Fixed: "Set up a device" now gives the Pi's IPv6 address too.** A router that hands out IPv6 (a BT Smart Hub does as it ships) also tells devices to use its own IPv6 DNS server, so a Windows laptop or Android phone set up for IPv4 only sent some lookups past QuietNet, and blocks and bedtime applied only some of the time. Each kind of device now gets the IPv6 step as well, with the choice of switching IPv6 off on the router (BT Smart Hub: Advanced settings, IPv6); if the Pi has no IPv6 address, the page says to switch IPv6 off on the router or accept that some lookups skip QuietNet.
- **New: a warning when the router names its own IPv6 DNS server.** On a Pi, QuietNet listens (never sends) for the router's IPv6 announcements, and the home page and "Set up a device" warn when they name a DNS server that is not the Pi. New `ipv6` part in `GET /api/status`.

Docker's firewall and "Cut live connections" (23 November):
- **New: the installer can make Docker's firewall let passed-on traffic through for good.** Docker drops traffic the Pi passes on, so "Cut live connections" asked people to run `sudo iptables -I DOCKER-USER -i wlan0 -o wlan0 -j ACCEPT`, and that was lost at every restart. After asking (or with `--yes`), the installer now adds a small systemd service, `quietnet-forward`, that puts this one rule back every time Docker starts, for the network connection the Pi reaches its router on. It lets through only traffic that comes in on that connection and goes straight back out on it.
